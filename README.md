## 这是什么

**全系统一条向量。** 所有用户的所有文件都按上传顺序**追加**到同一条向量
:math:`V = (V_0, V_1, \dots)` 的末尾，共用**一份**摘要
:math:`\delta = ((U, C), n)`、一套公开参数。

由此得到三个能力，也决定了本项目的全部形态：

| 能力 | 含义 |
|---|---|
| **常量摘要** | 客户端只保存 :math:`\delta` —— 两个群元素加一个整数，与文件大小、文件个数都无关 |
| **常量证据** | 一次打开的证据是 :math:`\pi_I = (S_I, \Lambda_I)` —— 两个群元素，与打开多少块无关 |
| **一个证据横跨多个文件** | 因为所有块都在同一条向量上，聚合天然跨文件、跨用户。这是选"全系统一条向量"而**不是**"一文件一向量"的全部理由 |

## 三个已定的设计决定

| # | 决定 | 含义 |
|---|---|---|
| 1 | **全系统一条向量** | 索引必须全系统唯一 ⇒ 必须有全局块索引登记表（`core/registry.py`） |
| 2 | **验证不受限** | :math:`\delta` 是公开的、验证是公开可验证的。任何用户都能验证任意位置的完整性 |
| 3 | **解密受限** | 块密钥被**所有者的 SM2 公钥**封装（`core/keywrap.py`）。只有那把私钥解得开 —— 这是密码学强制，不是一张表说了算 |

**这两个"受限/不受限"是两条独立的线**，也是本项目最需要讲清的一点：

```
验证 = 服务层说了算的程度很低（δ 公开）  →  密码学上挡不住，但它本来也不该挡
解密 = 密码学说了算                      →  就算服务器整个被拿走，没密钥也解不开
```

## 密钥那一层：块密钥是怎么被“锁”住的

### 它做什么

上传时每块都会现生成一把 16 字节的 SM4 密钥。这三件事**同时**发生：

1. 密钥拿去除掉这一段明文（SM4-CTR，每段独立密钥与 IV）；
2. 密钥被**用所有者的 SM2 公钥**封装成密文（`BlockRow.key_ct`）；
3. **明文密钥不落到任何地方** —— 它只在内存里活过一次封装的时间。

解密的唯一途径是**用所有者手里那把 SM2 私钥把封装解开**。

封装用的是 **ECIES**（`core/keywrap.py`）：

```
每次封装抽一把临时私钥 d，密文里带上 R = d·G
双方各算 z = d·pk_owner / sk_owner·R，值相同（都是 d·sk_owner·G 的 x 坐标）
SM4 密钥 = KDF(z, 加密标签)，密文体用 SM4-CTR 加密
tag      = KDF(z, 认证标签 ‖ R ‖ iv ‖ 密文体)
```

**为什么需要那个 tag**：SM4-CTR 本身**不提供完整性**。没有 tag 的话，
节点把密文体翻一位，解出来的块密钥就变成另一个值 —— 那个坏密钥会一路带到
SM4 解密，表现是“文件内容是乱的”，而不是“这里被篡改了”。有了 tag，
**篡改在解封这一步就现形**。

### “只有自己才能解密”不是一句话，是两处密码学

```
第 1 层 · 块密钥 ← 用**所有者的 SM2 公钥**封装
         别人的私钥对它无效 —— 不是“查表发现你没权限”，是**算不出来**。
第 2 层 · 用户私钥 ← 用**他自己的登录口令**封装（PBKDF2-HMAC-SM3 → KEK → SM4+tag）
         库里存的只有密文；明文私钥从来没落过盘。
```

第 2 层是“数据库被拿走也解不开”的落点：块密钥是用公钥封的，**光有数据库解不开**；
而能解开它的那把私钥，本身又是**用口令包着**的。口令不落库（库里只有它的
加盐哈希，那是登录校验用的另一回事）。

于是“登录”这件事有了明确的位置：**用口令把私钥解封出来，挂到这次令牌上**
（`users.sk_wrapped` → `StoreManager._keys`，**只在内存**）；退出登录把它丢掉。
丢掉之后连本人也解不开 —— 而他照样能验证，因为验证一个密钥字节都不碰。

### 两道门，但**判据只有一条**

```
① 应用层 can_decrypt   —— 你不是所有者就不是。提前拒 + 写审计 + 给一句人话，零密码学开销，
                          所以列表页渲染一把锁也不心疼。
② 密码学层 unwrap_key  —— 真的解不开。没有会话私钥 → 403 并叫你重新登录；
                          私钥不对 → 403 并说清“这不是你的密文”。
```

**保留两层是有意的**：它们**不是重复**，各管一件事 ——
应用层给得出“为什么拒”的好话术，密码学层才是**算不算得出来**。
只留 ① 的话绕过接口层直接读库就能拿到明文；只留 ② 的话用户只看到“算不出来”而不知道为什么。

反过来说，**绕过接口层直接改库也没用**：库里的 `key_ct` 封的是所有者的公钥，
你把某个字段改成能过快速门，密文照样解不开。有一条测试专门钉这件事
（`Test解密门::test_块密钥是拿公钥封的_库里没有明文密钥`），
另一条钉住“界面上的锁与真实解密结果**逐格一致**”。

### 四个刻意的取舍（都比原来更硬）

**一、管理员也解不开别人的文件。**
以前管理员靠 ABE 的**主密钥**（KGC 特权，能签发任意属性的密钥）解开一切。
现在没有这种东西了 —— 块密钥是拿**所有者的公钥**封的，**没有人**手里有第二把钥匙，
包括管理员、包括协调者自己。这实际上是安全性的提升：少了一个“能解开一切”的单点。

**二、没有全局主密钥文件。**
原来有一个 `abe_msk.json` 单独放着（它能解开任何密文，所以必须小心保管）。
现在**它不存在**：每一把私钥都由**它自己的口令**保护。

**三、改口令要重新封装私钥，而且只能自己改。**
只改 `pwd_hash` 的后果是：他下次登录口令对得上，却**解不开自己的私钥** ——
于是以前传的文件全部读不了，而报错看上去像密钥坏了。所以改口令必须
**用现在的私钥重新包一遍**；而“现在的私钥”只在**本人登录那一刻**进过后端内存，
所以管理员**改不了别人的口令**（后端直接 400 拦住，让他自己改；管理员可以停用他）。

**四、“授权共享”整个删掉了，不是留了个空接口。**
旧那套的每一步（用 msk 解出块密钥 → 按新策略重封）都依赖 ABE。
现在想再多封一份给某人，就意味着得**再多存一份块密钥密文** ——
那是一套新的数据结构，不是“保留接口”能顶上的。
（要恢复共享，正确做法是给 `blocks` 加一张“额外封装”表，而不是回到 ABE。）

### 一行代码验一下

```powershell
python demo.py   # 第 1b 节起就是密钥层：口令封私钥 → 公钥封块密钥 → 只有所有者解得开 → 篡改被抓
```

## 改一块 / 追加 是怎么做的

`PATCH /api/files/{id}`，用 `op` 选变体（不传就是 `modify`，所以老请求照旧可用）：

| `op` | 干什么 | 动了什么 |
|---|---|---|
| `modify`（默认） | 换**一块**的内容 | 那一块的密文/密钥/IV；`n` 不变、`C` 变 |
| `append` | 在**末尾追加**内容 | 只**新增**几块；`n` 变大 |
| `truncate` | 删掉末尾的块 | 那几块的密文与封好的块密钥都**真删**；`n` 变小。**只能删向量末尾**，见「已知局限 5」 |

两个变体的共同点：**已有的块一个都不动**，也不重新分发 —— 所以代价只与
"动了多少"成正比，与文件本身多大无关。这是 `upload` 里
「先 `split_segments` 切块、再逐块独立加密」这个顺序换来的：
每块一把 SM4 密钥、一个 IV，块与块互不牵连。

### `op=modify`：一次改块在四层上各发生一件事

| 层 | 发生什么 |
|---|---|
| 内容 | 那一块重新加密（**新密钥 + 新 IV**），明文长度可以变 |
| 承诺 | `δ = (U, C, n)` 里 **n 不变、C 变**；向量分量换成新的 `SM3(密文)` |
| 密钥 | 块密钥换了，所以**必须用所有者的公钥重新封一次** —— 否则新内容连他自己也解不开（忘了重封就会变成“他自己也打不开”，而那种故障很难归因） |
| 存储 | 只把新密文推给**持有那一块的那些**节点（有多份副本就推每一份）；它们自己算出新摘要，与协调者逐位比对 |

### `op=append`：只往末尾加块

| 层 | 发生什么 |
|---|---|
| 内容 | 新块单独加密，**新密钥 + 新 IV**；新块序号接着已有的往下排 |
| 承诺 | `δ` 里 **n 变大**（新块加在向量尾部）、`C` 随之更新；走的是 `add` 那条增量路径 |
| 密钥 | 新块各自用**所有者的公钥**重新封一遍，所以所有者在整个文件上都能解密（不会出现“老内容能读、追加的读不了”） |
| 存储 | 新块按轮转分片落到各台节点，有几份副本就写几份 |

三个容易误解的地方，界面上也写明了：

1. **追加不回头填上一块的空位。** 上一块宁可只写半截，也不去补它 ——
   补它就是一次 `modify`（要换密钥、要重推密文），那样"追加"就变成
   "先改块、再加块"了。代价是会留一点空隙：块按序拼接，内容一个字节都不会错，
   只是块会偏碎。所以**追加后的明文切法 ≠ 把两段拼起来重新上传的切法**
   （后者算出的 `C` 不同，只有 `U` 相同）。
2. **追加之后，这个文件的全局下标不再保证是一段连续区间。** 两次追加之间
   别的文件也占了位置，于是它会变成 `0-1, 12` 这种带缺口的集合。顺序仍是块序、
   拼接照旧正确；但界面上**不能**再拿 `first_index–last_index` 当区间 ——
   文件列表那一列已经改成显示真实集合了。
3. **旧证据必然作废** —— `δ` 里的 `n` 变了，而 :math:`S_I` 依赖 `n`。

### 块大小与「存到哪几台」都是**逐文件**的

上传时可选，不传就是部署默认值：

* `segment_bytes` —— 这份文件按多少字节切一块；
* `nodes` —— **这次只往哪几台机器上摊**（“手动指定分发”）。只勾几台，
  这份文件的块就**只**放在那几台上（其它机器一块也拿不到，但仍然会同步全局
  状态 —— 这条要是写错，之后验证会与没参与的机器对不上，是很难查的故障）；
  追加新内容时**自动跟着这份文件原来的机器**走。

  ``nodes`` 与 ``segment_bytes`` 不一样：它**不占一个字段**，而是从“这个文件
  的块实际在哪几台”**推**出来的（重启后由协调者库重建，推得与重启前一样）。
  台数变少时会自动滤掉已经不在集群里的机器。好处是不用改库表、不用迁移，
  而且“这份文件住在哪几台”永远与事实一致。

``segment_bytes`` 是**逐文件记下来的**（``files.segment_bytes``），所以：

* 以后改部署默认值**不会**把老文件弄坏；
* **改块与追加都按这份文件自己的值走**。

  > 这一条是本轮修掉的一个真实不一致：``VectorStore.modify`` / ``append``
  > 早先读的是 ``self.segment_bytes``（**向量当下的默认值**），而不是这份文件
  > 上传时那个值。表现是“改过部署默认值之后，老文件改不动 / 追加的块尺寸
  > 悄悄变了” —— 而且它不会报错，只会静静地把一份文件的块形状搞混。
  > 回归测试：``tests/test_store.py::Test块大小::test_改块与追加按文件自己的块大小``。

代价（界面上也写了）：块越小 → 块数越多 → 越容易撞上先定死的位置上限
``n_max``（而那时的报错看起来像“文件太大”，所以服务端直接在入口把范围说清），
但**单块改起来越省**；块越大 → 块数越少 → 上传与检索越快。

### 两个共同的坑（改块与追加都有）

1. **`content_digest` 不会更新** —— 它是**上传时刻**整份明文的 SHA-256，
   而协调者手里从来没有完整明文（只有各块的密文摘要），算不出新的整体摘要。
   "现在是第几版"看 `files.version`（上传为 1，每改一块/追加一次 +1，
   也是**防重放序号** —— 客户端只持摘要、看不到内容，察觉不到重放，
   所以序号得由协调者记）。
2. **旧证据会失效** —— 证据是 δ 的函数，而改块改了 `C`。证据池按 **δ 指纹**
   标作废，不是按 n（n 前后都是 12 也照样作废 —— 这正是必须换判据的原因）。

单进程模式下还有一个坑（已修）：节点那边的密文是协调者代为落库的
（`node_blobs`），而 `_persist_nodes` 早先只写"新下标"、用的还是 `db.add` ——
改块改的是**已有**下标，于是进程内一切正常、**重启后**才炸，而且症状极具
迷惑性：**第 2 层承诺通过，只有第 1 层块哈希失败**。现在它是 upsert 了。

## 存储证明（PoR）是怎么做的

`POST /api/por` —— 问的是**另一个**问题。这一节值得单独讲，
因为它和“完整性验证”在演示里最容易被混成一件事。

|  | 完整性验证 `POST /api/query` | 存储证明 `POST /api/por` |
|---|---|---|
| 问什么 | 你给我的这几块**对不对** | 你**还存着**吗 |
| 怎么问 | 客户端先说清要哪几块 | 服务端**随机点名** :math:`\lambda_{pos}` 个位置 |
| 取内容吗 | 取（客户端要拿密文做块哈希校验） | **一个字节都不取** |
| 谁回答 | 拿到证据的那几台 | **每一台**都答自己沾到的那部分 |
| 结论形状 | 一份证据 + 验证报告 | 合并成**一份**常数大小证明，验一次 |

判据两道（缺一条都不接受）：

1. ``Q = r`` —— 点名的位置**全收齐了**。这是主要的那个判据；
2. 合并出来的那份证据通过 ``VerRetrieve`` —— 内容没被换掉。

挑战由**服务端**随机生成，客户端只决定点多少个位置。
让客户端报下标反而是个漏洞：它可以专挑“节点一定存着的”那几个，于是什么都审不出来。

### 一个必然的设计选择：挑战按“主副本归属”拆开

开了副本之后同一个下标存在于多台上，而 ``PoS-Aggregate`` 要求各份额**互不相交**
（部分重叠时它宁可报错也不静默出错）。所以 ``VectorStore.pos_audit`` 把挑战切成
``r_node = r ∩ {i : 主副本(i) == node}`` 再分头发下去 —— 主副本集合天然是
``[n]`` 的一个划分，各份额必然两两不交。

代价要说清：**这只审计主副本那一份**。要连副本一起审计，
得按“第 k 份副本”分组再跑一轮 —— 结构上就是这个方法的自然推广，没做。

### 实地演示（跨进程、4 台真节点、每块 2 份副本）

* **正常**：挑战 ``0-2, 4, 7-8, 10, 12``（8 个）→ 4 台分别答 4/1/2/1
  （合计 8，互不相交）→ 合并了几份份额 = 4，而**证明仍是 256 字节** → 通过。
  发起人是 ``wangwu``（**非所有者**）—— “验证不受限”这条同样适用于它。
* **打死 node-1**（:math:`\lambda_{pos}` 取满 13）→ **不通过，缺 ``[0, 4, 8, 12]``**
  （正是 node-1 主副本的那 4 个），node-1 那行标「连不上」并带出具体错误，
  其余三台 3/3 答齐。

两个数字放一起才是完整的话：**PoR 点出“有一台没在答”，而数据本身还在**
（副本兜着 —— 同一次演示里那个文件照旧读得出、验得过）。
两条线各管一件事，这正是要把它们做成两个入口的原因。

## 已知局限（答辩要**主动**说，别被问出来）

排在前面的更值得主动交代。

### 1. 已经**切掉** ABE（老师要求）：换成了“公钥封块密钥 + 口令封私钥”

原来那一层是 CP-ABE：块密钥按访问策略封装（属性写在密钥里、策略写在密文里），
于是“两个各持一半属性的人把密钥拼起来”这件事只能靠**双线性配对**挡住 ——
项目里为此还带了 `core/fabeo.py` + 一整份 `_vendor/py_ecc`（**14.3 MB**）。

现在这一层整个去掉了（`core/abe.py`、`core/policy.py`、`core/fabeo.py`、
`core/vendor.py`、`_vendor/`、两个路由、三份测试全部删除），改成：

* 块密钥用**所有者的 SM2 公钥**封（ECIES，见 `core/keywrap.py`）；
* 用户私钥用**他自己的登录口令**封（PBKDF2-HMAC-SM3 → KEK）。

两条硬语义没变，而且更硬：**验证照样对所有人开放；解密只有所有者行** ——
现在连管理员也不行（没有能解开一切的主密钥了）。
**代价也照实说**：共享（把某一份文件给另一个人看）**没了**，
要恢复得给 `blocks` 加一张“额外封装”表。

### 2. 节点鉴权是**共享令牌**，不是每节点独立

``X-Node-Token`` 一个值全节点通用（演示级）。它能挡住"把 ``--host`` 改成
``0.0.0.0`` 就敞着"那类事，但挡不住内鬼横向移动。
生产应每节点独立、可轮换；再往上就是 mTLS。

### 3. 跨进程追加**没有事务、没有回滚**

``VectorStore._append`` 里 ``apply_append`` 是 k 次 HTTP：第 3 台失败时，
前两台已经推进到新 ``n``，而协调者内存还停在旧 ``n``。
启动闸（``_verify_nodes_at_startup``）会在**重启时**发现并拒绝启动，
但**运行期间**系统处于不一致、而且没有任何标记的状态。

> ⚠️ 因此**不要**笼统地说"任一台掉线不影响"。准确的说法是：
> **已经取到手的证据仍然有效**（这正是可聚合的价值），
> 但**追加时一台连不上，那一次追加会直接抛错**。

### 4. 副本是"防掉机器"，不是"防丢"—— 而且写入需要全员在线

**每块默认存 2 份，落在两台不同的机器上**（`Settings.replica_factor`，改配置即可调）。
这让"掉一台"变成可恢复事件：主副本连不上时读取会自动改问另一份副本，
已存数据照旧读得出、验得过。`tests/test_store.py::Test副本` 里有正反两条对照
（删掉一台的数据 → 有副本的读得出、单副本的真读不出），
`tests/test_replica_nodes.py` 还会**真的停掉一台节点进程**来验。

三点必须主动交代：

* **副本不占全局位置。** `n` 仍然是块数，不乘副本数 —— 不变的是 `n_max` 与证据大小
  （仍然是 2 个群元素），变的是**各节点自己的存储**（约等于翻倍）。
* **副本是同一份密文的拷贝，不是纠删码。** `replica_factor` 不能超过机器台数
  （否则"两份"会落在同一台上，掉一台一起没），代码在构造时就拒了。
* **写入仍然需要每一台都在线。** `apply_append` 要通知所有节点，一台连不上那次上传
  就失败。所以副本保证的是**已存数据**不丢、读得出来，**不**保证写入可用性。
  要真正的写入容错得先有共识/重试队列。
* 开副本**之前**传的老数据仍然只有一份 —— 这是合法状态，自检**不拦**它，
  而是由 `under_replicated()` 报出来在界面上提示（想补齐就重新传一次）。

### 5. 截断（删掉末尾的块）**现在能做了** —— 但只能删"向量末尾"

`PATCH /api/files/{id}` 带 `{"op": "truncate", "drop_blocks": n}` 能删掉这份文件末尾的 n 块；
界面上是文件详情页的「删掉末尾的块」。它**真的把数据删掉**（密文与封好的块密钥
都从库里删、节点侧也真删），不可撤销。

链路是三步（每一步都有非有不可的理由）：

1. **先让"部分相交"的节点把 K 那部分交回来**（`POST /node/drop`，即论文的 `RmvStorage`）。
   底层 `_apply_del` 要求每个节点与待删区间"要么全包含、要么全不相交"，
   而 4 台轮转 + 每块 2 份副本下，跨台的末尾区间几乎必然部分相交。交回是幂等的。
2. **协调者自己扮成"持有整个向量"的节点**来发起 `del`（`_push_del` 要求推送方持有整个 K，
   而跨台的末尾区间不可能由某一台完整持有）。
3. **推给每一台**（`POST /node/delete`）：节点自己算新 δ，并把被删块的密文真删掉。

仍然有两条限制，都必须对用户说清：

1. **只能删全局向量末尾的连续下标**（`_push_del` 里那句
   `tuple(K) != tuple(range(n - k, n))` 直接报错）—— 所以只有**最后写进向量的那份文件**
   才删得动尾巴。别的文件会收到 400，并**点明**是哪几个下标卡住；
2. **不能删到一块不剩**（向量不允许缩到 `n=0`）。整份删除是另一件事。

> 设计 B 本来就把"只能删末尾"写进代价里了（见下面「三条真实代价」第 2 条）。
> 现在这条从"明确不做"变成了"能做，且带一条使用前提"。
> 实测：`tests/test_truncate.py`(15) + `tests/test_api.py::Test截断`(7)
> + `tests/test_truncate_nodes.py`(2，4 台**真节点进程**)。

### 6. 证据是 **δ 的函数** —— 上传、**追加**和改块都会让旧证据作废

证据绑在全局摘要 :math:`\delta = (U, C, n)` 上，而它有两个会被改动的部分：

* **上传/追加**抬高全局块数 :math:`n`（:math:`S_I = g^{e_{[n]}/e_I}` 依赖它）；
* **改块不改变 n**，但会改变承诺 :math:`C`。

所以"看 n 没变就以为证据还行"是错的。界面上判断卡片作废用的是后端给的
**δ 指纹**（12 位十六进制，同时覆盖两件事），而不是 n；早先版本存的卡片
没带指纹，就标成"需重新取"而不是仮装它仍然成立。

这不是 bug —— 它是"全系统一条向量"换来的跨文件聚合能力要付的钱。

---

### 7. 需求 2 的另一半「不满足条件就不能**验证**」**没有做**

需求 2 的字面是「满足条件才能验证」。本项目选了「**验证不受限、解密受限**」，
所以**没有**在“发证据”那一步拦人。理由（答辩要主动说）：

* 同一份需求里另一处写着「内科护士只需要**查询并验证**密文的完整性，不需要解密」；
* δ 是公开的、验证是**公开可验证**的 —— 证据直接从节点就能拿，服务端“不发”拦不住谁；
* 真正**强**的门只有解密那道（密码学强制）。

代价：一个没有解密权限的用户，**照样能验证**任意文件的完整性（这正是演示的卖点之一）。
要真拦这一半，得把 `/api/query` 对普通用户关掉、只留“按文件取证据（先查所有者）”，
那就会把上面那条需求一起推翻 —— 这是**两个需求条目之间的选择**，不是漏做。

### 两种模式：单进程 vs 跨进程

|  | 单进程（默认） | 跨进程（设了 `VDS_NODE_URLS`） |
|---|---|---|
| 节点是什么 | 同一进程里的 4 个 `NodeState` 对象 | 4 个独立进程，各自一个 `node.db` |
| 协调者拿到什么 | 直接访问 `transport.states[nid]` | 只能 HTTP 说话（`HttpTransport`） |
| 节点状态 / 密文存哪 | 协调者库里（`node_state` / `node_blobs` 表） | **各节点自己的库里** —— 协调者那两张表空着 |
| 代数结果 | 与跨进程**逐位相同**（有测试钉住） | 同上 |

切换只需要设/不设一个环境变量。**两种模式的库不能混用**：协调者启动时发现
库里还留着单进程模式的节点状态，会直接拒绝启动（`--reset` 重来）。

> **有副本：每块默认存 2 份，落在两台不同的机器上。** 所以删掉一台的数据目录，
> 数据还在 —— 读取会自动改问另一份副本（`tests/test_store.py::Test副本`
> 有正反两条对照），跨进程模式下还可以直接停掉一个节点进程试（`tests/test_replica_nodes.py`）。
> 副本数由 `VDS_REPLICA_FACTOR` / `Settings.replica_factor` 定，上限是机器台数。

| POST | `/api/query` | 登录 | 按**全局下标**验证（**不受限**） |

### 批量验证的实测结论（规划 P1 第 7 条：**不做**）

规划里写着「跨文件批量验证（随机系数把多条方程合成一条模幂）」。
这种事不能先写代码再找理由，所以先写了 `scripts/bench_batch.py` 去**量**它。
`|N| = 1024, l = 256, n = 64 块 / 8 个文件`：

| 做法 | 耗时 | 说明 |
|---|---:|---|
| 一次查全部 64 块（**一份**证据） | 2097.7 ms | 设计 B 的主路径，跨文件天然合成一份 |
| 逐块各查一次（64 份单块证据） | 5022.0 ms | 比合一份**慢 2.4 倍** |
| 逐份 `svc.verify`（64 份已有证据） | 318.4 ms | 主路径上"验证"那一栏 |
| 验证**一份**覆盖 64 块的证据 | 331.0 ms | 与上一条同量级 —— 代价看**块数**，不看份数 |
| **批量方程**（两条信道都合，随机系数） | **684.7 ms** | ⇒ **慢 2.15 倍** |

**为什么批量反而更慢**：本项目的 `svc.verify` 已经把论文里"先重建每个
:math:`S_i` 再乘起来"的 O(ℓ\|I\|²) 换成了 `add_back` 链的 **O(ℓ\|I\|)
次小指数模幂**（注释在 `svc/scheme.py::verify`）。批量法必须回到
"少次、但每次指数有 :math:`|I|(\ell+1)` 位"的形式，模幂次数差不多、
指数却大了一个数量级 —— 于是净亏。

对照脚本里还带一条**反面对照**：故意翻掉一个值，批量检查必须拒（否则说明
"批量"那个实现本身是坏的，那前面的数就不能信）。脚本里两条信道（`S` 与 `Λ`）
是**都合**的 —— 只合 `S` 那条会"看起来快 1.4 倍"，但那是因为它少验了一半。

**而"跨文件"那一半收益早就拿到了**：一次查询就是一份证据覆盖多文件
（表里第一行 vs 第二行差 2.4 倍），这才是规划那条真正想要的东西。

## 设计 B 的三条真实代价（必须知道）

### 1. 每次上传都是一次全网事件

:math:`n` 一变，:math:`e_{[n]}` 就变，于是**每台服务器**的
:math:`S_I = g^{e_{[n]}/e_I}` 与 :math:`\Lambda_I` 都可能失效，必须全网同步。
这就是为什么追加走的是论文 §8.2 的两段式更新（`PushUpdate` / `ApplyUpdate`）
而不是本地改个变量。

代价量级：**≈ 块数 × 服务器台数** 次 `ShamirTrick`。演示里一个 5 块的文件耗时 1271 ms
（前一个 3 块的文件只要 393 ms），就是这个原因。**追加同理**：它走的是同一条
`add` 路径，代价只与新块数有关，与文件原有大小无关。

一个漂亮的例外（`tests/test_store.py` 里有专门断言）：**收到新块的那一台，它的
:math:`S_I` 反而不变** —— :math:`e_{[n]}` 乘了 :math:`e_j`，:math:`e_I` 也乘了 :math:`e_j`，比值恰好抵消。

**拆成独立进程后，这条代价从"函数调用"变成了真网络往返**：一次追加 = 4 次
`POST /node/append`（每台一次，且每台都要把**全部**新值收下 —— 见
`core/transport.py` 开头的 warning）。所以跨进程模式的写延迟由**节点台数**决定，
与单进程模式的差别不是“一点点”。好消息是**读**不贵：检索只在拿到证据的那几台
上打 `POST /node/retrieve`，证据聚合是在协调者本地做的。

### 2. 只能删末尾

`del` 是截断语义（`_push_del` 只认 `tuple(K) == tuple(range(n - k, n))`），
所以中间的文件只能**标记删除**，位置收不回来。

代价上跟了两条：① **截断已经做了**（见「已知局限 5」），但它只认**全局向量末尾**
—— 所以只有最后写进向量的那份文件才删得动尾巴；② 逐节点的 `ApplyUpdate` 还要求
每个节点与 K "要么全包含、要么全不相交"，而轮转分片 + 副本之下这条几乎必然不满足，
所以**删之前要先让那些节点把那部分交回来**（`POST /node/drop`，论文的 `RmvStorage`）
—— 也就是说，一次跨台的删除是"交回 + 一次删除"两轮节点侧交互，比改块/追加重。

### 2.5 副本不占位置，但占存储

`n` 仍然是块数、不乘副本数，所以承诺、证据大小、`n_max` 都不受副本影响；
受影响的是**各节点自己的存储**（副本倍数）与**写人的要求**（每台都要在线）。

### 3. `n_max` 一旦定死不可改

隐藏阶群方案的结构性约束：素数一旦选定，:math:`U` 就绑死了，事后无法凭空增加位置。

## 三条安全红线

1. **DB 只存 `N`、`g`、`l`、`n_max`**，绝不存 `p`、`q`、`φ(N)`。
   知道 :math:`\varphi(N)` 就能求 :math:`e` 次根 ⇒ 能**伪造任意证据**，方案彻底失效。
   `core/session.py::crs_to_dict` 只导出那四个公开量，有测试钉住这一点。
2. **RNG 种子必须为 `None`**（走 `os.urandom`）。固定种子 = 知道种子的人能重跑出
   `p`、`q` = 等价于泄露 :math:`\varphi(N)`。
   （对照：旧演示前端的 `seed: "web-demo"` 就是这条红线的反例。）
3. **大整数一律按十进制字符串传**。Python 的 `json` 能处理任意精度 `int`，
   但 JS 的 `Number` 只有 53 位有效精度 —— 群元素一过前端就丢精度。

## 两层验证（为什么缺一层都有洞）

查询回来的是**向量分量**（密文摘要），所以验证分两层：

| 层 | 查什么 | 挡住什么 | 谁来做 |
|---|---|---|---|
| 1 · **块哈希自洽** | :math:`\mathrm{SM3}(\text{密文段}) = \text{收到的分量}` | 拿别的段的密文冒充（`demo.py` 第 7b 节） | **协调者**（见下） |
| 2 · **向量承诺** | :math:`S_I^{e_I} = U` 且 :math:`C = \Lambda_I^{e_I} \cdot \prod_{i \in I} S_i^{y_i}` | 节点偷改自己存的分量（`demo.py` 第 7 节） | `svc.verify`（协调者调） |

第 7b 节是重点：**第 2 层会通过**，因为承诺的对象是摘要、摘要没被动 ——
所以"有了向量承诺就不用做块哈希"是错的，两层必须都在。

**为什么第 1 层是"协调者算"而不是"客户端算"**：密文段压根不下发给浏览器，
浏览器只拿到一个布尔值（`hash_layer_ok`）。位置也是对的 ——
**协调者正是不信任节点的那一方**，该由它核对"拿回来的密文对不对得上分量"。
真要客户端自己算，就得把全部密文段下发到浏览器，那反而多泄露一层。

## 实现要点（改动过算法核的地方）

1. **`vds/updates.py` 两处性能补丁**：`_push_add` 与 `_apply_add` 原本用
   `pow(U, e_K // e_j, N)` 逐个算新位置的成员见证，代价是 O(k) 次
   「指数长 (k−1)(l+1) 位」的模幂 —— `k=1024, l=256` 时单次约 1.2 秒，
   整批十几分钟。改成 `batch_root_factor_any`（同一文件 154 行已在用的同一原语）
   后降到 O(k log k) 次乘法 + 少数几次幂。语义完全不变，384 个回归测试全部通过。
2. **`δ_0 = (U=g, C=1, n=0)`**，不是论文 §8.2 写的 `(1, g)`。
   那个写法是"文件还没建立"的占位约定，不满足 :math:`U_n = g^{e_{[n]}}`，
   从它出发做 `add_back` 会得到 `(1, g^{e_0})`，两项都错。
   `tests/test_store.py::Test摘要不变式` 断言增量结果与一次性 `commit` 逐位相同。
3. **素数表全局缓存**（`core/session.py::get_primegen`）：`svc.setup()` 每次都新建
   `PrimeGen`，而它是惰性的（构造 0 ms），成本全在第一次 `first(n)` ——
   `n=1024` 时 1442 ms。不缓存就是每个文件白花 1.4 秒。
4. **把节点的状态机抽成 `core/node_state.py`**（步骤 2b 的前一半）。
   原来 `VectorStore` 自己拿着一份 `dict[node_id, LocalView]` 并直接改它，
   于是“节点自己跟上更新”在代码上并不成立。抽出来之后：

   * `NodeState` 只认“你负责哪些位置”与“发生了什么”，新状态**自己算**；
   * `NodeTransport` 只有五个方法，而且**没有一个能让协调者改节点状态** ——
     如果协议里有一条 `set_state(...)`，这个抽象就是摆设；
   * 两种实现（`LocalTransport` / `HttpTransport`）**共享同一份 `NodeState`**，
     否则本地模式迟早变成“另一个简化实现”，两条路径静默分叉。

   测试把这件事钉住了：把**同一批分量与密文**分别喂给两种传输，
   全局摘要与各节点状态必须**逐位相同**（`tests/test_nodes.py::Test两条路径一致`）。
5. **协调者的库里不再存节点状态与密文**（步骤 2b 的后一半）。
   `NodeBlobRow` / `NodeStateRow` 只在单进程模式下才有行；跨进程模式下一个行都没有
   （`tests/test_api_distributed.py` 直接查表断言）。这是“拆进程”是不是真的做到了
   的可检查判据 —— 否则只是把同一份数据**存**了两遍。
6. **节点会自己比对摘要**。`NodeRuntime.append` 里除了把收到的 :math:`\Delta`
   拿来用，还要用本地状态**独立算出一份新摘要**与之逐位比对，不一致就 409 并拒绝落库。
   盲信协调者给的摘要就等于放弃了这条性质，而且后果要等到检索时才暴露。
7. **启动时的三道闸**：节点名单与地址必须一一对应（`check_node_config`）；
   公开参数必须能交给每台节点（连不上就拒绝启动）；跨进程模式下
   **每台的 ``n`` 必须与协调者相等**（不相等说明节点丢过库或连错了协调者）。
   都是“宁可当场报错，也不要半死不活”。
