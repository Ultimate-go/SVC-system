### 读路径也打通了

`store.query` 现在两条路都通（验收第 6 节覆盖）：

* **同一份文件**：把各节点的凭证聚合起来（节点真的参与了证明，快）；
* **跨多份文件**：在「合并位置集」上重算证据 —— 承诺用增量乘
  `C_merged = ∏ C_f^{E/E_f}`，份额用 `open_subvector` 重算（秒级）。

同一轮里修掉三个隐蔽的坑（细节见第四节）：

1. `_push_mod` / `_push_add` / `_push_del` 的 `new_delta` 忘了带 `offset` ——
   节点是按 `offset` 存视图的，于是新文件的「空视图」会注册到 `offset=0`，

## 四、已定下的设计决策（接续时必须遵守）

1. **位置是若干段的并集**。追加时原段末尾可能已被后来的文件占住 ⇒ 新块**另起一段**。
   数学不受影响：`E = ∏_{j∈P} e_j`，`P` 是一段还是几段都一样。

2. **两套下标不能混** —— 这是本次改造最容易错、且错了不报错的地方：
   - **文件内局部块号**（`0..n-1`）：只喂给 `svc` / `vds` 层（它们假定下标密集，`lambda_subset` 里就有 `range(n)`）。
   - **全局位置号**：记账用（`values` / `_holder` / `_replicas` / `_plan`）与对外接口（`query` 的 `indices`）。
   - 映射关系：`全局位置 = positions_of(文件)[块号]`；"第 i 块 ↔ 素数表第 offset+i 个"由**素数视图**承担。

3. **位置段永不回收**。删文件 / 截断只让段变短或消失，位置不再分给别人
   —— 回收会让同一个位置对应上两个不同的素数，而两份承诺可能同时存在。
   于是 `n_max` 的含义变成「**全系统位置总预算**」（各文件块数之和 + 历史空洞），已由 8192 调到 65536。

4. **跨文件聚合**：承诺用**增量乘** `C' = ∏_f C_f^{E/E_f}`（一份一次模幂），
   证据在“合并位置集” `P`（= 涉及文件的**全部**位置）上**重开**（`open_subvector`）。

   **为什么不能把两份文件的现成证据直接 `agg` 起来？** 不是缺一个算法，而是论文的聚合
   **以同一个承诺 C 为前提** —— 学位论文 `Def. 29`（Aggregatable Subvector Openings）原文：
   「any commitment C and triple (I, v_I, π_I) s.t. Ver(pp, C, I, v_I, π_I) = 1 …
   for any (J, v_J, π_J) such that Ver(pp, **C**, J, v_J, π_J) = 1 …」。
   一文件一向量 ⇒ 每份文件各有 `C_f` 与 `U_f = g^{E_f}`：

   * `S` 抬得动：`(S_I)^{E/E_f} = g^{E/e_I} = U'^{1/e_I}`；
   * `Λ` 抬不动：`Λ_I = (∏_{j∈pos(f) 里不在 I 的部分} S_j^{v_j})^{1/e_I}` 的支撑集
     **只覆盖本文件的补集**，不含另一份文件的块 ⇒ `Agg` 里“用 ∏φ_j^{v_j} 抵消交叉项”
     那一步**没有东西可抵消**，差额正是“对方文件那些块的 1/e_j 次方”，隐藏阶群里求不出来
     （`svc/groups.generate_primes` 明确丢弃 `φ(N)`；保留陷门则会架空“存储节点不可信”）。
   * 要补齐那一半，只能**知道合并集里所有块的值**、在合并向量上重开 —— 所以这条路的
     代价是 **O(Σ_f |f|)**，**与“你要验几块”无关**（只跟涉及文件的总位置数有关）。

   **实测拆解**（2026-10-05；l=256 / |N|=1024 / 4 节点 / 2 副本 / HTTP 传输；
   每行取 4 块，其中 2 块来自两份不同文件）：

   | 涉及文件 | \|P\| | 取回密文 | 合并 C' | 重开 Open | 验证 | 合计 |
   |---|---|---|---|---|---|---|
   | 只 t28KB（同一份文件，走 agg 不重开） | — | 338 ms | — | — | 12 ms | 538 ms |
   | t28KB + t18KB | 46 | 465 ms | 79 ms | 523 ms | 21 ms | 1194 ms |
   | t28KB + test_50KB | 78 | 776 ms | 144 ms | 1037 ms | 20 ms | 2137 ms |
   | t28KB + test_64KB | 92 | 930 ms | 164 ms | 1273 ms | 21 ms | 2573 ms |

   “重开 Open” ≈ **12 ms / 位置**，随 `Σ_f |f|` 线性增长 —— 这是跨文件路径唯一的结构性代价，
   也是优化的着力点：按论文 §6.4.2 的 (A)+(B)，先对合并向量做一次
   `disagg_one_to_many` 得到逐位置证据，之后每次查询只用 `agg_many_to_one` 合起来
   （小指数，毫秒级）。

   > 同一次实测还暴露一个**与跨文件无关**的浪费：「取回密文」被**重复取副本**放大了一倍
   > —— `core/store.py::_fetch` 会向每位持有者都取一遍（实测 `count=4`，本可 2 次）。
   > 已单独记录，待修。

   **判据推广（2026-10-05）**：「一次结论」的前提不是“同一份文件”，而是**同一个
   ``(U', C')``** —— 即“哪条向量”。于是：

   * 一张**归约出来的跨文件卡**本身就能一次结论（它的位置全落在合并向量上）。
     接口实测：宇宙 = `[admin/t28KB, wangwu/t18KB]`、46 个位置、`merged=True`，
     批量 24 ms / 逐份 16 ms。
   * 多张**各绑自己文件承诺**的卡仍然合成不了一条方程（Def. 29 的同一个 ``C``）——
     要么分开验，要么先用「聚合选中」并成一张再验那一张。

   实现见 `core/store.py::universe_for`（**单文件时退化为那份文件自己** —— 两条路
   因此是同一段代码，单文件走的仍是 ``crs_n_for`` 的快路）与

## 五、已知的坑（都踩过）

★ **最新（同一个坑踩了两次）**：给带 `__slots__` 的类加字段，**必须同时把字段名
加进 `__slots__`** —— 否则**赋值的那一刻**就抛
`AttributeError: 'X' object has no attribute '新字段'`。这个报错看起来像“字段没定义”，
其实只是“槽位没开”，很容易往错的方向查。

这次是 `core/store.py` 的 `VectorStore.__slots__`：原本写着 `"delta"`，改成按文件的
`deltas` 时忘了动它 —— 而**紧挨着它的注释里恰好就写着上次踩过的同一句教训**。
结论：动任何类之前先看一眼它有没有 `__slots__`。

- `svc` 层**假定下标密集**，所以"全局唯一的稀疏位置号"喂不进去 ⇒ 必须用**素数视图**承担映射，`svc/` 一行都不用改。
- `replace` 的搜索串里**不要放中文弯引号**（`"…"`）：它和直引号长得像，但匹配不上，会以"找不到匹配"的形式失败。
- `self._delete_tail(K, _settle)` 在 `truncate` 与 `delete_from` 里**各有一份**，替换时要带上下文。
- `store.py` 的方法里 `self.delta` 已全部换成 `self.deltas[file_id]` / `delta_of()`，
  若看到残留的 `self.delta` 就是漏改点（用 `grep 'self\.delta\b'` 复查）。

### 4. 本轮新踩的坑（4 个都是真 bug，全部由"跑起来"发现）

1. **整段被删光时只归一成空视图，不改数据结构** —— `NodeState.apply_delete` 把
   视图清空（`n=0, I=()`）却把键留在 `self._views` 里，落库、重启、读回来之后
   启动自检报 `node-1 停在 [... (10, 0)]，协调者是 [...]` 并**拒绝启动整个后端**。
   协调者那边的账目（`FileDeltaRow`）在文件被删掉时是**直接删行**的 —— 两边对
   "现在有哪些段"必须一致。修法：`n == 0` 就把整段摘掉（`_forget_segment_if_empty`）。
   *发现方式*：拿"上传一个探针文件再删掉"当冒烟的收尾动作，后端就再也起不来了。

2. **用 `range(g0, store.n)` 算要删的位置** —— 位置段**永不回收**，删过的位置会留
   下空洞。一个"删掉又重传"的探针文件拿到位置 11、而块数也是 11，于是
   `range(11, 11)` 是空集，自检报"连带名单不一致"。修法：`K = tuple(rec.indices)`
   （就是这份文件自己的全部位置），与核心层 `delete_from` 用同一个来源。

3. **改造漏改的未定义变量** —— `manager.verify_batch` 里 `K_set` 从未定义，
   一调就 `NameError` → 500。跨文件的一次性验证走 `/api/query`，所以一直没暴露。

4. **逐份审计的返回值没有顶层汇总字段** —— `pos_audit` 改成逐文件之后只返回
   `{ok, files, message}`，而路由 / 前端 / 冒烟读的一直是顶层的
   `shares` / `challenge` / `Q` / `proof_size_bytes` → `/api/por` 500。
   修法：在 store 里合成一次（并且 `shares` **按机器归并**，否则 5 份文件会打出
   20 行同样的 `node-1..4`）。

- **自检的报错必须带差异**。`"名单与核心层报的不一致"` 这句话第一次真触发时，
  我盯着它只能猜 —— 它连是哪两个集合都没打出来。补上两边内容后一眼看出
  `K=[]` vs `K=[11]`，根因随即浮出。
- **改大 `.vue` 文件之前先列出它已有的标识符**。验证页里 `filesApi` 与 `loadFiles`
  都已经存在，我加的 import 与函数各撞了一次（`vue/compiler-sfc` 的报错很直接，
  但白跑了两轮构建）。而且它**本来就有** `allFiles` + `loadFiles` —— 正确做法是
  复用，不是另拉一份列表（两份列表会出现"这边刚传的文件那边还没有"）。
- **冒烟脚本里的旧期望要跟着架构改**：`kw["users"] >= 5`（新 seed 只有 3 个账号）、
  用两个**不同文件**的卡片做"批量验证"（新架构下一次只能覆盖一份文件）——

## 七、收尾：补跑两条没人跑过的路径，抓出第 5 个真 bug

上一轮"全部通过"其实有三块没验到，这一轮补齐：

### 1. ★ 跨进程自检（4 台真节点 + 真 HTTP）—— 抓出真 bug

上一轮我只改了 `core/node_state.py`，**只跑了单进程的 smoke**。补跑跨进程立刻炸：

```
[9] 截断末尾 1 块成功 ...                    ← 过
[10] 删除 bob/b.txt → WriteError: 有节点没能跟上这次删除
     node-1..4 全部拒绝 /node/delete：500
```

原因：`node_service/server.py` 的 `/node/delete` 路由在 `apply_delete` **之后**还要
`delta_of(off)` / `I_of(off)` / `describe(offset=off)` 去写库、拼响应；而 `n = 0` 时
`NodeState` 已经按第 1 条坑的修法把**整段摘掉**了 ⇒ 那几个调用全部 `KeyError` ⇒ 500。

**为什么单进程测不出来**：`LocalTransport` 直接调方法、不经过 HTTP，摘段之后没人再去读它。

- `node_service/persist.py` 新增 `delete_state(offset)`：删掉某段的 `state` 行
  （协调者那边是直接删行的，两边对"现在有哪些段"必须一致）；
- `/node/delete`：`has_view(off)` 为假时走"整段已摘掉"分支 —— 删库里的行、
  返回 `n=0 / held=0`，**不再**去读一个已经不存在的段；
- 节点启动恢复：跳过 `n == 0` 的段（老库或半途失败可能留下），顺手删行。

修后同一组自检 **11/11 全过**（含改块 / 追加（另起一段）/ 截断 / 删除 / 收尾自检）。

## 八、性能：上传为什么随库里已有块数增长（已修），以及素数表的待办

### 1. 先回答那个疑问：承诺确实是分开的，但写路径上有一处**全量自检**

提问是："每个文件的承诺是分开的，理论上上传时间只跟文件大小有关，为什么后面的文件还是很慢？"
**直觉是对的，密码学那部分确实与全局无关** —— 实测（4 块文件、2 副本、4 台）阶段耗时：

| 偏移 | 总 ms | `承诺（push_update）` | `分发到节点` | pow 调用数 |
| --- | --- | --- | --- | --- |
| 0 | 223 | 75 | 121 | 148 |
| 24 | 379 | — | — | — |
| **64** | **822** | 57（**平**） | **708** | **492** |

`承诺` 恒定 ⇒ 承诺确实跟着文件走。涨的全在 `分发到节点`，而 profiler 指出是
`builtins.pow` 的**调用次数**从 148 涨到 492 —— 同样 4 块，多出来的 pow 全花在
**校验历史数据**上。

根因：`core/transport.py::LocalTransport` 在写完之后调的是**无参** `state.check()`，
它按 :meth:`NodeState.check` 的语义遍历该节点持有的**全部位置段**、逐段跑密码学验证。
于是**每上传一个 4 块的文件，都要把全库所有块重验一遍** ⇒ 单次写操作 O(全库块数)。

而同一个文件里的 `drop()` 用的是 `state.check(offset)`（只查被改动的那一段，正确）；
跨进程那条路（`node_service/server.py` 的 313 / 401 / 537 行）**本来就是** `check(off)`
—— 所以这个缺陷是 **`LocalTransport` 独有**的，跨进程模式反而没中招。

修法：`adopt` / `apply_append` / `apply_update` 三处改成 `state.check(offset)`，
与 `drop` 对齐。语义不变（本次只碰了这一段；全量核对仍然由管理员自检
`store.check()` 与启动自检兜底）。

**后果（实测同一支 benchmark）**：偏移 64 的 4 块上传 **822 ms → 184 ms**，
pow 调用 **492 → 148**；偏移 64→108 连续 12 次 **166-186 ms 完全平**，
不再随库里已有多少块变化。

### 2. 第二个原因：257 位素数的惰性生成 + **翻倍预扩**（★★ 已修，见本节的「已实施」）

`svc/primegen.py::PrimeGen` 是惰性的、带累积缓存，`_extend` 每次**翻倍**预扩。
实测代价：

- `is_probable_prime_screened` **67.8 µs/候选**；257 位素数密度 ≈ 1/178
  ⇒ **约 5-7 ms/个素数**（实测：扩到 512 个用 2.77 s，1024 个用 3.6 s）；
- 于是**每跨过一个 2 的幂**，就有一次上传要独自承担"补一批素数"：
  跨进程实测 6 次上传里出现 643 ms 与 896 ms 两个尖峰（其余 280-430 ms），
  位置恰好是 16 与 32 的边界 —— **不是随偏移单调上涨，而是阶梯式尖峰**；
- 位置总预算 `n_max = 65536` ⇒ 若真的用满，累计素数生成 **约 6-8 分钟**，
  摊在各次上传里就是若干次长卡顿；
- 而且素数表**只在内存里**（`_PRIMEGEN_CACHE`）：后端或节点一重启就从头再来。

★★ **2026-10-05 已实施 ① + ②**（③ 仍然只是建议）：

* **① 素数表落盘共享**（`core/session.py::_PersistentPrimeGen` / `warm_prime_cache`）：
  缓存文件默认 `.primecache/primes-b257.txt`（640 KB，**只在本地**、已进 `.gitignore`；
  可用 `VDS_PRIME_CACHE` 覆盖）。协调者与 4 台节点启动时都只是“读回来”：
  **8192 个素数 47.81 s → 0.062 s**；1024 个档 **5.75 s → 0.047 s（122×）**。
  ★ 素数序列与现场重算**逐位相同**，所以已有数据、已有 CRS 完全不受影响。
* **② 精确扩容**（`svc/primegen.py::PrimeGen.get` 不再翻倍预扩）：
  要第 100 个就只算到 100 个（旧实现会算 128 个），跨过 2 的幂不再有生成高峰。
* **落盘的四道校验**（把它当**不可信输入**）：头三行（位长 / 个数 / sha256）、
  严格递增与位长区间、**前 8 个与现场重算逐位相同**、均匀抽样 8 个做素性测试；
  任何一道不过就丢弃重算并重写文件。原子写（`*.tmp<pid>` + `os.replace`）、
  节流（个数涨到 1.5× 才写，8192 个全程只写 ~13 次）、盘上更多就不写（不倒退）。
* **验收**：`scripts/seed.py --reset --demo` 在**单进程**与**跨进程**两种模式下各跑通
  （3 个账号 + 5 个文件 + `[check] 自检通过`；跨进程经 HTTP 查询 / 验证 / PoR 全过，
  证据仍 256 字节）；篡改一个素数 / 截断 / 改位长三种伪造一律回退重算。
* **启动时预热**：`start_all.py` 新增 `[2/6] 素数表（预热）`（按当前用量自动，
  至少 256 个；`--warm N` 可指定，`--warm 0` 跳过）。

* **S1 · 内存里的 `deltas` 与库里的 `file_deltas` 没跟着改**。后果不是"少了个字段"：
  运行期 `delta_of(墓碑名)` 直接 KeyError（文件列表 500）；重启后 `_reload` 从
  `blocks`（墓碑名）与 `file_deltas`（旧名）重建出**两套身份**，而且**不自愈**。
  → `core/store.py::rename_owner` 现在一并重挂 `deltas`（键是 `(owner, file_key)`），
  改名操作同时更新 `blocks` / `files` / `file_deltas` **三张表**。
* **S2 · 整件事在锁外面做**（路由层直接 `mgr.store.rename_owner(...)`）。
  → 搬进 `StoreManager.delete_user`，在 `self._lock` 内完成；异常则回滚改名，
  不会留下"内存改了、库没改"的中间态。
* **S3 · `_finish()` 没有保护**。向量层推成功、库落盘失败时异常直接冒出去，
  留下"向量是对的、库里什么都没有"的半截状态 —— 而重启是**从库重建向量**的。
  → 新增 `_finish_or_pending()`：失败就把回调记进 `self._pending_finish` 并在响应里
  报 `persist_error`，等 `retry_push()` 补上；5 个调用点（上传/改块/置零/截断/删除）
  全部改用它，`retry_push()` 也去掉了原先的 `had_pending` 前置门（那会让补推永远不触发）。

**验收**：用一个零副作用的进程内测试（`VectorStore.__new__` + 假的 registry）核改名结果 ——
`files` 与 `deltas` 的键都变成 `('tomb#1','f1')`；三个文件的正常上传/改块/截断/删除路径全过。

### 10.2 客户端锚定：δ 不能从服务端来（S4）

**这是本轮最要紧的一条。** 增量承诺的基底 δ（`U_n` / `C`）原先**直接采信服务端**。
可本系统的前提是"服务器不可信" —— 服务端只要换掉 δ，客户端算出来的证据照样"验证通过"，
整套可验证性就退化成一个口头承诺。

→ 前端加了**第二层本地锚定**（`frontend/src/utils/anchor.js` 的 `vds_delta_anchor_v1`）：
首次见证成功时把 δ 钉下来（TOFU），此后**一律以本地 δ 判决**；服务端给的 δ 只当对照，
单独报成 `remoteVerify`。不匹配时详情页给出**红色**说明而不是一句"验证通过"。

**验收**：新增 `frontend/tests/delta-anchor.test.js` —— 服务端改 δ ⇒ 本地 δ 仍判
`verify.ok === true` 而 `remoteVerify.ok === false`；改密文 ⇒ 本地 δ 直接拒（`verify.ok === false`）。
另有 offset>0 回归与"下标越界"两个用例。

### 10.3 输入校验与健壮性（P6 等）

* **P6 · 超长十进制串直接 500**。`backend/schemas.py` 里那些大整数是用**字符串**传的
  （`S_I` / `Lambda_I` / 证据卡取值 / 位置向量），没有长度上限 ⇒ 一条超长串会在
  `int()` 那一步炸成 500（Python 3.11+ 的整数转字符串限制是 4300 位）。
  → schema 层加 `MAX_INT_CHARS = 512` 与 `DecStr`（`StringConstraints(max_length=512)`）；
  解析层再加一道 `manager._to_int()`，把 `ValueError` 统一翻成 `OutOfRange`。
  **实测**：超长串现在返回 **422 `string_too_long`**，不再是 500。
* **P11 · 前端的十六进制解析不严格**。`hexToBytes` 原来靠 `parseInt` 拿到 `NaN`、
  再被 `Uint8Array` 静默变成 0 —— 于是 `keywrap.js::field()` 的形状校验被绕过，
  错误一路拖到 tag 不匹配才现形，报的是"密文被改过"，指不到"你传了个非法十六进制串"。
  → 现在逐对字符校验 `/^[0-9a-fA-F]{2}$/`，不合法立刻抛错，语义与后端 `bytes.fromhex` 对齐。
* **`mod(x, m)` 模数为 0 时**原来会走进死循环/静默错值 → 现在直接抛"服务端给的公开参数不合法"。
* **`verifyEvidence` 加了下标越界检查**：越界报 `BAD_SHAPE`「下标 X 越界：这份文件的向量只有 N 个位置」，
  而不是算出一个看似正常的错误结论。
* **上传体量**：`files.py` 改为 `file.file.read(MAX_UPLOAD_BYTES + 1)` 再判断，
  避免"先全读进内存再拒绝"。
* **位置区间解析**：`parseIndexRange(text, maxCount = 8192)` 在**展开之前**先算
  `b - a + 1 > maxCount`，并做累计检查 —— 否则 `0-99999999` 这类输入会先把内存撑爆。
* **指标标签**修正：`append` / `truncate` 两条路径原先记错（`_do_truncate` 记成了 `append` 的同名标签）。

### 10.4 身份与密钥（I1、I8、I7）

* **I1 · 退出登录不吊销令牌**。JWT 是无状态的，"登出"只是客户端删掉 token，
  服务端照样认 —— 令牌被别人抓到时"登出"没有任何作用。
  → `security.create_token` 加 `jti`；`StoreManager` 维护内存里的已作废表
  （`_revoked: jti -> exp`，按 exp 自动清理）；`/api/auth/logout` 写入作废；
  `deps.current_user` 校验，命中返回 **401「这张令牌已被作废（已退出登录），请重新登录」**。
  **实测**：登录 → `/api/auth/me` 200 → `logout`（返回 `token_still_valid: false`）
  → **同一个令牌再访问 `/api/auth/me` 得到 401**。
* **I8 · 默认模型下改口令这条路是死的，而且会把人逼回"私有钥交给服务端"**。
  默认模型（`server_key=false`）后端**不持有私钥**，旧实现要求 `session_key_of(token)`
  不为 None 才允许改口令 —— 那在默认模型下恒为 None ⇒ 改口令必然 403。
  用户唯一的出路是先用 `server_key=true` 登录一次 —— 也就是**习惯性地把私钥交回服务端**，
  整套"服务端不掌握私钥"被绕过。
  → 改成"**浏览器封装、服务端只登记**"：前端在本地用新口令把私钥重新封好
  （`frontend/src/utils/crypto/keywrap.js::wrapPrivateKey`，与 Python
  `core/keywrap.py::wrap_private_key` 形状逐字节一致），把密文交给
  `PATCH /api/admin/users/{id}` 的 `sk_wrapped`；后端 `StoreManager.rekey_with_blob`
  只验两件事：**① 新密文能用新口令解开；② 解出来的私钥还是原来那把**
  （拿 `users.pub_key` 对拍）。②这一条不能省 —— 少了它，攻击者把自己的私钥封装后交上来，
  这个账号名下的文件就全归他了。
  * 口令哈希与私钥密文**同生同死**（同一事务提交）：分开写会留下"新口令过不了哈希、
    旧口令解不开密文"的**死账号**。
  * 前端配套：`stores/crypto.js` 的 `unlocked` 成为**唯一判据**；`stores/auth.js` 在
    登录/登出时正确建立与清除本地密钥；侧栏与个人中心的"有没有私钥"不再看
    `session_key`（那个字段在默认模型下恒为 false，会把"已解锁"和"没有私钥"同时显示出来）。
  * **实测（浏览器，真实路径）**：zhangsan 在个人中心改口令 → **HTTP 200**
    （`timings.total_ms ≈ 808`，`pub_key` 未变）；随后
    ① **旧口令解不开新密文**（`KeyWrapIntegrityError`）、
    ② 新口令解得开、
    ③ **解出的私钥与未改动的 `pub_key` 一致**（= 私钥本体没变，已上传的文件一把都不用重传）、
    ④ 旧口令登录 **401**、新口令登录成功。验证完把口令改回演示值。
* **I7 · 节点令牌**（**只做了缓解，没有做隔离**）。令牌是**环形**的（节点之间互相校验），
  现在只做三件事：① 不打印、不进命令行（只走环境变量与 `nodes/token.txt`）；
  ② 文件权限收到 `0o600`（类 Unix 生效）；③ **轮换路径写进文档**：停服务 →
  删 `nodes/token.txt` → 重启，`load_token()` 会生成新的并统一发给后端与全部节点。
  * **为什么不做"一节点一令牌"**：那要求把分发与轮换做成 N×N 矩阵，配错的代价是
    "某两个节点互相拒收"（现象是"数据莫名其妙推不过去"，极难查），而它的威胁模型是
    "防局域网内有人随手调节点接口"，**不是**"防本机同用户" —— 同一用户本来就能读
    后端进程内存、读协调者库。**这一条属于"已知未闭环"，如实记在这里。**

### 10.5 自查发现的一条（审计报告没提）

**`openBlocks` 按 `globalIndex` 取证据值，而 `proof.I` 是文件内局部下标。**
任何 `offset > 0` 的文件（本项目演示数据里的 `test_64KB` 就是，offset=28）都会因此
取错位置，表现为解密预览/验证结果不对甚至直接报错。
**实测**：`proof.I = [0,1]` 而 `global_index = [28,29]`。
→ 改为按 `b.blockIdx` 映射，并加了回归测试。

### 10.6 本轮**没有做**的事（如实列出）

* **`.paper/` 目录**：审计建议清理。复核后决定**保留原状**并在文档说明 ——
  它是投稿材料的原始副本，删掉不可逆；其中不含密钥、口令或用户数据
  （已逐文件确认），风险等级低于"误删作者材料"的代价。
* **三处审计结论与代码不符**：已在复核阶段指出，未做代码改动。

## 十一、第二轮审计整改（2026-10-05 晚）

又做了一轮独立的只读审计（27 条，S / P0 / I / N 四组），**审的正是第十章那轮修复的边界**。
逐条回到源码复核后：**报告基本属实**（只有 N3 一条我原本有异议，最终按折中方案改）。
本轮最重要的结论是：**上一轮的 δ 锚定漏掉了信任根**。

### 11.1 S1（严重）：δ 锚只钉了 `(U, C)`，没钉住群参数 `N`

验证等式 `S == U_n`、`Λ == C (mod N)` 里的 `N` **本身就是方程的一部分**。
上一轮把 δ 钉在了本地，却让 `N` 每次从 `pack.crs.N` 现取
（`anchor.js::setDeltaAnchor` 只存 `{U, C, n, fp, source}`）。

于是被控服务端可以**自选一个已知阶的 `N'`**（例如 2048 位素数，群阶 `N'-1` 已知），
用已知阶反解出 `S_I` / `Λ_I`，让 `addBack` 链**恰好**收敛到钉住的 `(U*, C*)` ——
"验证通过"与"δ 一致"**同时成立**，而密文是它随便给的。这是**静默的假阳性**。

修法（P0-1 / P0-2）：

* `anchor.js` 新增**第三层锚** `vds_crs_v1`（系统级：`N` / `l` / `prime_bits` / `prime_start`），
  并把 `N` 一并写进 δ 锚；
* `openBlocks` 改为「本地有锚就用**本地的** `N`；与远端对不上就**直接拒绝**」
  （不像 δ 那样"再用远端验一遍" —— `N` 变了就是换了考场，用新 `N` 重验毫无意义），
  返回值新增 `crsVerdict: 'no-anchor' | 'match' | 'mismatch'`；
* `primes.js` 新增 `checkModulus(N, {bits})`：奇数、`> 2`、位长与声明一致、不被前若干小素数整除；
* `checkPrimes` 增补：`start` **必须**等于 `2^{bits-1}`，并与本地锚记的起点一致。

**验收**：新增回归用例「服务端换掉群参数 ⇒ 必须直接拒绝」与「明显假造的 N 被拦下」，
**92/92** 通过。

**诚实边界（应写在界面上）**：这能抓住"**中途**换 N"与"明显假造的 N"，
**抓不住**"服务端从第一天就给一个形状合法的恶意 N" —— 那要求 `N` 有**独立于服务端**的来源
（部署配置 / 出带分发 / 客户端自生成）。

### 11.2 S2（严重）：证据池路径没有本地验证 —— 本轮只做"降级表述"

本地验证原先只在 `views/files/detail/index.vue` 一处被调用；证据池是一条
**完全采信服务端 `ok`** 的旁路（`stores/pool.js` 把 `/api/query` 的响应原样塞进卡片，
`views/evidence/pool/index.vue` 的 `batchResult.ok` 直接驱动绿色成功样式）。

本轮做了报告说的**第一步**：把两种**可信级**分开 —— 证据池的结论明确标注
"服务端结论（未经本地验证）"，不再与详情页那句"本地验证通过"共用同一套成功样式。

**未做**：把 `/api/query` 也接上本地验证（需从节点取回密文；跨文件场景还要取回
各文件 `C_f` 与位置段以复算 `C'`）。报告也建议单开一个迭代 —— 它的工作量与前两条
不是一个量级。

### 11.3 重要问题（I1–I5）

* **I1 · 撤销表只在内存**（这是上一轮做的）。原注释写"重启后密钥会变、令牌本来就失效"
  —— 那句话只在**没设** `VDS_SECRET_KEY` 时成立。设了它之后签名密钥跨重启不变，
  令牌照样有效，而撤销记录随进程消失 ⇒ 已登出的令牌**复活**。
  → 新建 `revoked_tokens(jti, sub, exp_ts, before_ts, revoked_at)` 表，内存那份降级为缓存。
  **实测**：登出后库里出现 `('gJ7m…', 'wangwu', …)`，同一令牌再访问得 **401**。
* **I2 · 改口令 / 停用不撤令牌**。"改了密码却赶不走对方"是个很危险的空档。
  → `StoreManager.revoke_user_tokens(username)`：JWT 是无状态的，服务端**没有**
  "某人签过哪些令牌"的记录，所以退回**时间戳黑名单**（记下"该用户在此刻之前签发的
  全部作废"，校验时比 `iat`）。改口令、停用、改角色三处都接上。
  **实测**：停用 `wangwu` 后，他**已经拿到手**的旧令牌立刻 **401**。
* **I3 · 4 个字段没有上界**：`FileQueryIn.block_indices`、`ProofIn.I`、
  `DecryptIn.indices`、`FilePatchIn.data_b64`（后者还带 `b64decode` 校验器）。
  → 前三个补 `max_length=MAX_INDICES`（8192），`data_b64` 补 `MAX_B64_CHARS`（12 MiB，
  与 `MAX_UPLOAD_BYTES` 对齐）。
* **I4 · 没有 ASGI 层的请求体上限**：`MAX_UPLOAD_BYTES` 是在**处理函数里**施加的，
  而那时请求体**已经被完整接收**（Starlette 的 multipart 会用 `SpooledTemporaryFile` 落盘）。
  → `backend/main.py` 加中间件，按 `Content-Length` 在进入路由**之前**拒掉。
  **实测**：声明 `Content-Length: 999999999` ⇒ **413**。
  **边界**：不信 `Content-Length`（chunked）的客户端绕得过；硬上限要落在反向代理或 uvicorn 参数上。
* **I5 · TOFU 静默钉扎**：首次见证不告知用户。**本轮未改** —— 它需要一套界面文案与
  交互设计，留在下一轮。

### 11.4 普通问题（N1–N7）

| 编号 | 修法 | 说明 |
|---|---|---|
| N1 | `guard.js` 的 `JSON.parse` 包 `try/catch`，坏数据视为未登录并清掉 | 不再整站白屏 |
| N2 | `randomBytes` 无 WebCrypto 时**抛错**，不再静默退回 `Math.random` | 真实浏览器 / Node 18+ 均不触发 |
| N3 | 改为「**闲置 15 分钟**锁 + **绝对上限 2 小时**」，取用私钥时 `touch()` 续期 | ⚠️ 报告建议的"只续期"会**削弱**这条纪律，故两条都留 |

## 十二、界面反馈整改（2026-10-06）

### 12.1 「试解密」永远报错（一个必然失败的按钮）

`files/list` 的「试解密」调的是 `filesApi.decrypt`（**服务端**解密），而默认模型下
后端**不持有私钥** —— 所以它**必然** 403。旧注释写的是"点下去才看到后端真的拒了你
（演示亮点）"，那是**旧模型**（后端扣着私钥）的说法。
→ 改走**客户端**路径：取密文 → 浏览器解封块密钥 → SM4 解密 → 顺手本地验证。
弹结果框（字节数 / 本地验证结论 / δ 钉扎状态）并把开头 48 字节显示出来 ——
明文**真的**是在浏览器里解出来的。非本人文件明确提示"拿不到块密钥，但完整性验证是公开的"。

### 12.2 块分布矩阵显示不全 + PoR 挑战没有说明

* `BlockMatrix` 写死 `maxCols: 30`，超出部分**静默丢弃**（界面上看不出还有没显示的）。
  → 默认 200（不直接全量是因为位置预算是 8192，一次渲染会卡住自己），
  并**显式**告知"只显示了前 N 个位置，还有 M 个未显示" + 「显示全部」按钮。
* PoR 那块原来只有标题 + 按钮。→ 补四段说明：它验什么（节点是不是真的还存着）、
  流程（随机抽样 → 交密文 → 协调者**自己重算**分量对拍）、数字怎么读
  （「问到 N / 答到 M」，M&lt;N 就是答不上来）、以及**诚实边界**
  （只是抽样，**不能**推出"它一块都没丢"）。

### 12.3 验证页版块重排

顺序改为：**拉取文件列表** → 查登记表 → 按文件 + 第几块验证 → 按指标筛选文件 → 集合。
「拉取文件列表」从"筛选块右上角一个小链接"提成**最上面的独立版块**
（带"已拉取 N 份文件 / 共 M 块"），因为它是后面所有版块的**前提**。

### 12.4 证据池：单文件 / 跨文件**分组显示**

两类卡的性质不同，混在一个列表里看不出"这张卡在说谁"：

* **单文件**：卡上就是那一份文件自己的向量承诺，聚合走同一向量内的 `VC.Agg`；
* **跨文件**：后端走 `_prove_merged`，把各文件承诺**抬进一条合并向量**后开证据 ——
  它的下标属于那条合并向量，**不是**任何单份文件的下标（分解时也不能按单文件块号切）。

→ 分两组、各带一句说明，单文件在前（组内保持原顺序）。
**实测**：`单文件证据 → 取回：test_20KB 第 0 块 → 跨文件证据（合并向量） → 跨文件取回：test_20KB 第 0 块；test_50KB 第 0 块`。

### 12.5 跨文件证据取回只拿到第一部分

`fetchOne()` 里 `targets` 写死成 `[[f.owner, f.file_key]]`（**只传一份**）——
而后端 `/api/query/files` 本来就收一个**数组对**，支持跨用户、多份文件聚合成**一份**证据
（`verify.py` 的文档写得很清楚）。所以"A 与 B 聚合出来的那份证据"在池子里
永远只能重新取回 A 那一半。
→ 文件选择改**多选**（`el-select multiple` + 折叠标签）：
选 A + B 就是"这两份文件的这一批块"的**联合**证据。
块号上限取**各份文件里最小的块数** —— 一个块号要对每份文件都成立，
拿最大的当上限会放过"在块数少的那份上越界"的写法，而那种错要到后端才报、
报的还是内部坐标，看不出是哪份文件的问题。
**实测**：选 `test_20KB` + `test_50KB` 取回 → 一份联合证据，
标题「跨文件取回：test_20KB 第 0 块；test_50KB 第 0 块」，**验证通过**。

### 12.6 旧数据：服务端返回改块前的内容

内容锚原先只存**当前一份**哈希，拿到旧数据时能说出的最多是"这和我上次见到的不同"。
→ 锚保留**前 4 版**哈希（`anchor.js` 的 `history` + `matchHistory()`）；
命中历史版本时**明确报出**：

> 服务端交回来的内容命中了你在 X 分钟前改过的那一版（改块，第 N 版）：
> 这是**改块前的旧数据**（回滚或缓存了旧版本），不是当前版本。

性质从含糊的"内容不对劲"变成确定的"**服务器拿旧数据搪塞我**"。

### 12.8 补正：`/api/query/files` 的 `block_indices` 语义不够（**接口级**）

**用户报的问题**：拿一张「50KB 第 0-49 块 + 64KB 第 0-63 块」的**聚合卡**点“取回”，
拿到的却是 `test_20KB` 第 0 块 —— 完全对不上。

**根因在接口，不在界面**：`block_indices` 当时只有**一种**形态 ——
“对**每个** target 都取这几块”（`manager.query_files` 的注释写得很明白：
“对每个文件都取一遍”）。而**聚合卡每份文件覆盖的块号是不同的**，
所以它的范围**根本表达不出来**；界面上的“取回”又只能读顶部那个文件框，
于是就成了“点 A 的卡，拿 B 的证据”。

**修法**（接口 + 界面）：

1. **接口支持两种形态**（`FileQueryIn.block_indices`）：
   * `[0, 1, 2]` —— **共用**（老语义，保留）；
   * `[[0, 1], [5, 6]]` —— **与 `targets` 一一对应**，第 i 组只作用于第 i 个 target。
   组数与 `targets` 不符直接 **400**（绝不静默取错范围）。
   归一化落在 `StoreManager.normalize_block_plan()`。
2. **卡片上新增「按卡重取」**：用它自己覆盖的“哪几份文件的哪几块”重新取一份 ——
   这才是“取回”在直觉上的意思，也是唯一能表达聚合卡那种范围的做法。
   （顶部取回区继续管“我**指定**范围取一份新的”；两件事分开。）

**过程中的一个真错误**：`query_files` 里**第二处**（`detail[].block_indices`）
我没有一起改，`int(k)` 收到 list → **500**
（`'<=' not supported between instances of 'int' and 'list'`）。
接口级验证时抓到并修掉了 —— 这说明**改接口不能只改主路径**。

**实测**：

* 接口：一一对应 `[[0,1,2],[10,11,12]]` → `test_50KB → [0,1,2]`、`test_64KB → [10,11,12]`；
  共用 `[0,1,2]` → 两份都是 `[0,1,2]`；组数不符 → **400**。
* 界面：取 `test_50KB 第 0-4 块` + `test_64KB 第 10-14 块` → 聚合 →
  在聚合卡上点「按卡重取」→ 新卡 `indices = [20-24, 80-84]`，
  **与原卡范围逐位一致**、验证通过（来源标记变成「按卡重取（跨文件归约）」）。
  **★ 注**：该「按卡重取」按钮在后一轮按用户要求**已删除**，见 12.9。

### 12.9 「分解（跨文件）」—— 改为按选中文件走「取回」

**用户要求**：去掉「按卡重取」；做**两个**分解——单文件的、跨文件的；点跨文件分解后**弹框选拆哪一份文件**。

**关键区分**（我一开始讲错过一次，这里记清楚）：

* **纯代数分解**（`/api/evidence/disagg`）：不取数据，在旧证据上做代数拆。
  它**要求这批下标只属于一份文件** —— 因为要拿**唯一一份文件**的素数视图算 `crs_n`，
  而且"局部号 ↔ 全局号"的换算也要那份文件的上下文。跨文件卡（合并向量上的证据）
  **走不通**；而且它拆出来的东西属于**合并向量**，不是任何单份文件的。
* **取回**（`/api/query/files`）：向节点**要密文**重新算一份证据。产物属于
  **那份文件自己的向量** —— 能独立验证、能再聚合。

**所以「分解（跨文件）」按后者实现**：选一份文件 →
`queryFiles([[f.owner, f.file_key]], 它在那张卡里覆盖的块号)` →
得到一份属于**该文件**的单文件证据。改动只在 `confirmCrossDisagg()` 一个函数里。

**★★ 必须防的坑（上一版真出过）**：targets **只能**用弹框里选的那一份，
**绝不能**碰顶部的文件选择框 —— 否则就会出现"拿 50KB+64KB 的卡去拆、结果取回了 `test_20KB`"。
代码里专门写了注释钉住这一点。

**实测（浏览器，正反各一次）**：

* 池子里放 `test_50KB 第 0-2 块` 与 `test_20KB 第 0-2 块` 两张单文件卡 → 聚合成一张跨文件卡；
* 拆 **20KB** → 弹框显示「拆出 test_20KB 第 0-2 块（3 块）」→ **只有 20KB 那张卡**被刷新；
* 拆 **50KB** → 弹框显示「拆出 test_50KB 第 0-2 块（3 块）」→ **只有 50KB 那张卡**被刷新；
* 两张拆出来的卡都 `stale: false`、验证通过。**没有任何"选 A 得 B"**。

**顺带**：「按卡重取」按钮与 `refetchLike()` 已彻底删除（`grep` 无残留）。

### 12.10 池子判"卡作废"的判据修好了（**改块也能抓到**）

`stores/pool.js::staleIds` 的注释本来写着"判据是 δ 指纹，不是 n（改块改 C 不改 n）"——
**思路是对的，但两处叠加的错误让它从来没生效过**：

1. 池子页调用时传的是 `pool.syncDelta({ fp: null, ... })` —— **指纹恒为 null**，那条判据永不生效；
2. `addCard` 里 `syncDelta({ fp: card.fp })` 把 `currentFp` 写成"**最后加的那张卡的**指纹"——
   而 δ 现在是**逐文件**的，根本不存在"一个全局指纹"。

**结果**：退化成只比 `n`。而**改块 / 清零 / 追加 / 截断都不改 `n`**
⇒ 改完块，池子里的卡看着一切正常，**实际已经验不过了**。

**修法**（纯前端；后端 `status.delta.files[].delta_fp` 早就有了，是前端没用）：
按"**这张卡覆盖的每一份文件**，它当时的指纹 vs 现在的"判 —— 任一份变了就作废。
`syncDelta` 新增 `fileFps`（`"owner/file_key" -> fp`），并一起持久化
（否则刷新页面后会先退化成比 `n`，要等一次 `/api/status` 才恢复）。

**实测**：重传文件后刷新页面，`fileFps` 拿到 `test_10KB / test_20KB / test_50KB` 三份的指纹，
**三张卡全部显示「已作废，需重新取」**。

**★ 仍未闭环的一处**：`disagg`（单文件分解）走的是纯代数，它的判据是
`disaggCardFresh`（比 `card.n` 与 `pool.currentN`）—— 改块同样不改 `n`，
所以**单文件分解弹窗里那句"这张卡已作废"也抓不到改块**。这一处没有一起改，
留给下一轮（判据应与 `staleIds` 统一）。


**先摆清现状**（它决定了能做到什么程度）：

* 解密在**服务端**做（`POST /api/files/{id}/decrypt`，私钥是登录时用口令解封后
  扣在后端内存里的）—— 明文由服务器给出；
* 验证也在**服务端**做（`/api/query` 的 `ok` / `verify` 是协调者代验的结果）；
* 前端**没有任何密码学依赖**（只有 axios / element-plus / pinia / vue），
  既解不了密，也验不了证据。

⇒ “明文没被篡改”这件事，客户端只能靠**自己留的独立记录**来判，不能靠服务器。

**做法（已实现）**：`frontend/src/utils/anchor.js` + `views/files/detail/index.vue`

1. 写块时（改块 / 清零，内容是自己给的，不需要信任服务器）把 `SHA-256(明文)`
   连同当时的 `version` / `delta_fp` / 来源 存进 **localStorage**（“锚”）；
2. 「改一块」页签新增 **「取回旧内容（并校验）」**：调
   `POST /files/{id}/decrypt {indices:[块号]}` 拿这一块的明文 → 算 SHA-256 →
   与锚比对 → **先给结论，再把内容填进输入框**（就地改最顺手）；
3. 三种结论：✅ 与本地记录一致（显示锚的时间与来源）／⚠️ 不一致（并列两个哈希）／
   ℹ️ 本地没记录（明确说“这一刻判不了”）。

**它证明什么、不证明什么**（界面与本文档必须同时说清）：

* 证明：现在拿到的那一块与**我上次见证的那一份**逐字节一致 → 防替换、防回滚；
* 不证明：**第一次**看到的内容就是原始内容 —— 那要求客户端**自己解密、自己验证据**
  （论文的 `ClntNode.VerRetrieve`）。这是下面说的“阶段 2”。

**实测（2026-10-05，`admin/t28KB` 第 0 块）**：① 无锚 → ℹ️，并把旧内容
（1024 B 全 `A`）填进输入框；② 改写成 `HELLO-FROM-CLIENT` 后版本 1→2、
δ 指纹 `a392037fd9fc`→`8dfffa520620`，锚写入
`{sha256: 5d7e0fa3…, version: 2, bytes: 17, source: 改块}`；
③ 再取回 → ✅「与本地记录一致 · 17 B · SHA-256 5d7e0fa3dd782653…」；
④ 人为改坏锚（等价于“服务器换了内容”）→ ⚠️「与本地记录不一致」并并列两个哈希
—— **检测确实生效**。

**阶段 2（还没做；做完才算真正的“服务器完全不可信”）**：

1. 后端给一条“取回**密文**”的路（密文本就存在不可信节点上，不构成新泄露）；
2. 前端引入 `sm-crypto`：SM2 解封块密钥 + SM4 解密 + SM3 算分量；
3. 把 `svc` 的验证（`VerRetrieve`）port 到 JS/WASM，由浏览器拿公开的 δ 自己验证据；
4. 私钥留在客户端（登录时在浏览器里解封，而不是扣在后端内存）。

这四步做完，“第一次看到的内容”也才能被证明 —— 工程量与风险都远大于阶段 1。

## 十、阶段 2：把解密与验证搬进浏览器（“服务器不可信”真正成立）

### 10.1 为什么非做不可

第九节的锚定只能回答一件事：“**你见证过**的那份内容有没有被悄悄换掉”。
它**回答不了**：“我**第一次**看到的内容是不是真的。” 原因在结构里：

* 解密在**服务端**做（`/api/files/{id}/decrypt`，私钥是登录时解封后扣在后端内存里的）；
* 验证也在**服务端**做（`/api/query` 返回它算好的 `ok` / `verify`）；
* 前端**零密码学依赖**（只有 axios / element-plus / pinia / vue）。

⇒ 服务端想给你什么就能给你什么，浏览器手里**没有任何独立判据**。
“服务器不可信”这句话在这种结构下无从谈起。

### 10.2 四步怎么落的

**① 取密文的路（不解密）**

* `core/store.py::cipher_of` —— 只取密文段 / IV / 明文长度 + 一份证据
* `backend/manager.py::cipher_pack` —— 再补上块密钥密文（`blocks.key_ct`）、CRS（N/g/l）、δ（U/C/n）、素数
* `POST /api/files/{id}/cipher`（仅所有者）

交出去的**全部是可被客户端独立校验的材料**；**不给**任何明文、不给任何解开的块密钥。
一个细节：`element`（分量）虽然带上了，但标注为“服务端声称的”——
浏览器**必须自己从密文重算**（`elementOf`），UI 只拿它做对照。

**② 浏览器里的密码学（纯 JS，零依赖）**

`frontend/src/utils/crypto/`：`sm3.js` / `sm4.js` / `sm2.js` / `pbkdf2.js` /
`keywrap.js` / `verify.js` / `primes.js` / `index.js`。

两处**最容易写错、且必须与后端逐字节一致**的地方：

1. **KDF 是 `SM3(shared ‖ counter_be32 ‖ info)`，计数器从 1 起**（`core/sm2.py::kdf`）。
   它不是 GM/T 0003 示例里的排布 —— “照标准写”会得到一个完全不同、但同样长度的密钥流。
2. **SM4-CTR 把整个 16 字节 IV 当大端计数器**，每块递增、进位跨字节
   （`cryptography` 的 `modes.CTR` 行为）。不是“只用低 32 位”，也不是小端。

底层群是 **RSA 隐藏阶群** `Z_N*`（`svc/groups.py`，无配对），
所以第 ③ 步在浏览器里只需要 **BigInt 模幂** —— 不需要 WASM，也不需要配对库。

**③ 浏览器验证据**

`verify.js::addBack` 严格照 `svc/scheme.py::add_back`：

```
S' = S^{e_i} mod N
Λ' = Λ^{e_i} · S^{v_i} mod N      // 用的是**更新前**的 S
```

处理完 `I` 里每个位置后终判 `S == U_n` 且 `Λ == C mod N`；
两条等式**分开报**（`BAD_S_I` / `BAD_LAMBDA`），所以能说到“是哪一步没过”。

**④ 私钥留在客户端**

* 登录默认 `server_key=false`：后端**不解封私钥**，只把**私钥密文**（`users.sk_wrapped`）
  放进响应（`key_blob`）；此后后端内存里**没有任何私钥**。
* 浏览器用同一个口令解封（`frontend/src/stores/crypto.js`）——
  口令就在手上（刚输过），所以不需要让用户再输一次。
* 私钥**不进 localStorage、不进 Pinia state**，只活在当前页面内存里；退出登录一并丢掉。
* 旧路径保留但**必须显式开启**（登录时传 `server_key=true`），只用于并排对比两种模型。

### 10.3 对齐测试（“不是猜的”的根据）

* `scripts/gen_crypto_vectors.py` —— 用 Python 侧实现产出**权威测试向量**
  （`frontend/tests/crypto-vectors.json`）。
  它刻意用**小参数**（65 位素数 / 256 位模数）：要钉的是**代数**，
  而 Python 生成 512 位素数要分钟级（这也是项目要做素数表落盘 + 预热的原因）。
  真实量级由 10.4 的端到端验证覆盖。
* `frontend/tests/crypto.test.js` —— **74 个断言**（含原有 54 个，全部保持通过）：
  SM3 6 条 · SM4-CTR 4 条（含跨分组与对合） · KDF 3 条（含跨块计数器） ·
  SM2 公钥与双向 ECDH · 块密钥解封 3 条 + 篡改一位必拒 · 私钥解封 2 条 + 口令错必拒 ·
  PBKDF2 确定性（迭代数真的参与） · 分量 3 条 · 素数检查（合数被抓 / 位长 / 区间 / 单调） ·
  证据验证（应通过 / 值被改→`BAD_LAMBDA` / `S_I` 被换→`BAD_S_I` / 密文改一位→拒） ·
  现场重算素数与前缀逐位相同。

### 10.4 实测（2026-10-05，浏览器里真跑，不是模拟）

| 素数素性检查 | 28 个全部通过（27 ms） |
| 分量比对 | 浏览器自己从密文算的 **与服务端声称的一致** |
| ⟹ 服务端在整条路上**没有参与任何秘密** | 它只提供了密文与公开参数 |

浏览器本地跑完 28 块（28 次素性检查 + 28 次 SM2 块密钥解封 + 28 次 SM4-CTR 解密
+ 28 次 `addBack` 模幂）**总共 109 ms** —— BigInt 在 1024 位模数下完全够用，
不需要 WASM，也不需要配对库。

「取回旧内容（并校验）」在**本地无锚**时给出的结论（如实、不夸大）：

> 本地没有这块的哈希记录（文件是在别的浏览器传的？）。不过这次的密文已经
> **通过浏览器本地的证据验证**（分量自己算、对本地 δ 校验），所以“交付的字节
> 没被换”是确定的；只是“它是不是你当初写的那一份”无法判断。

回归：`npm --prefix frontend test` → **74/74 通过**（含原有 54 个）；
`npm --prefix frontend run build` → exit 0。

### 10.5 能力边界（写清楚，不夸大）

* `checkPrimes` **发现不了“下标与值错位”**：`{0,2,3}` 配 `{e0,e1,e2}` 三项单调、
  位长对、都是素数 —— 输入本身不含“第 2 个位置该配哪个素数”这个信息。
  **但它也不构成漏洞**：`U_n` 与 `C` 是由**正确**的素数序列定义的，
  换一个素数算完 `addBack` 链必然对不上，验证会拒绝。
  它真正拦的是**合数**（合数会让 `shamir_trick` **静默**算错）。
* 默认路径下**素数表来自服务端**（形状 + 素性检查）；
  `primesFrom()` 提供现场重算那条完全独立的路径，但它是显式选择（慢）。
* **δ 仍然由服务端交来**（`cipher_pack` 里的 `delta`）。
  这一条是下一个该补的口子：论文里 δ 本来就是**客户端自己保存**的
  （`ClntNode` 只持有 `δ = ((U,C), n)`）。
  只要 δ 由服务端提供，一个**足够恶意**的服务端仍可伪造 (U,C) 让任意内容通过验证。
  真正收口要做的是：**第一次见证时把 δ 锚在本地**（第九节那套锚定的推广），
  之后一律用本地 δ 验证，与远端 δ 不一致就报警。

### 10.6 安全模型对比

| | 旧（服务端解密） | 新（浏览器解密） |
| --- | --- | --- |
| 私钥在哪 | 后端内存 | 浏览器内存（不落盘） |
| 谁能解密 | 后端**代**你解 | 只有浏览器 |
| 验证在哪 | 后端（`ok` 字段） | 浏览器（`addBack` 链） |
| 服务端能作恶到哪 | 给你**任意**明文 | 只能给一份**过不了验证**的应答 |
| 登录的贵的那一步 | 后端 20 万次 PBKDF2 | 浏览器 20 万次 PBKDF2 |
| 刷新页面 | 私钥还在（后端） | 私钥没了，要重新登录 |
