# 开发与验收记录

本文件记录**当前版本可执行的验收项、判定标准与失败处理方式**。
它不含改动时间线；每条结论都对应一个可重跑的命令或一个已存在的测试文件。

---

## 一、验收总览

| 层级 | 手段 | 是否需启动服务 | 通过标准 |
|---|---|---|---|
| 算法内核 | `verify_identity_primegen.py` 等 5 个 `verify_*` | 否 | 退出码 0，逐条 PASS |
| 业务流 | `verify_store_identity.py`、`verify_fault_drill.py` | 否 | 同上 |
| 接口层 | `_e2e_api.py` | **是** | 退出码 0 |
| 静态一致性 | `check_*.py` 四项 | 否 | 打印"全部一致/全部通过" |
| 前端单元 | `npm --prefix frontend test` | 否 | 162 条全过 |
| 性能标定 | `bench_*.py` | 否 | 产出数据，供文档引用 |

约定：所有 `verify_*` 与 `check_*` 都是**只读或自建临时数据**，不会破坏 `vds.db` 中的现有内容。

## 二、坐标迁移的五道关卡

"去掉全局下标、改为按块身份派生素数"是一次涉及全链路的改造。以下五关逐层向上，任何一关失败都说明上层结论不可信。

### 2.1 第一关：算法内核（`verify_identity_primegen.py`）

判据是**双轨对照**：同一份数据，用旧的分配式素数映射与新的身份式映射各跑一遍，
提交、打开、验证、聚合、分解的结果必须**逐位相同**。

失败含义：换素数映射后密码学内核算不出或验不过，后续改造全部免谈。

### 2.2 第二关：会话层（`verify_session_identity.py`）

验证 `core/session.py` 能在两套坐标系之间切换，且**老路径逐位不变**。
判据包括：同一块在新旧两条路径上取到同一个素数、老路径的输出与改造前完全一致。

### 2.3 第三关：存储业务流（`verify_store_identity.py`）

把身份坐标接进 `VectorStore` 的真实业务流，逐项确认：
上传、改块、追加、截断、聚合、分解、删除之后，承诺与证据仍然自洽；
删除后重新上传同一块，得到的仍是同一个素数（无空洞）。

### 2.4 第四关：后端落库与重启（`verify_backend_identity.py`）

前三关都在进程内，这一关用**真库 + 模拟重启**，确认身份字段完整落盘。
失败症状是"重启后这份文件忽然验不过"——离线单测发现不了。

### 2.5 第五关：跨进程线格式（`verify_node_wire.py`）

唯一真的走 HTTP 的一关：不起端口、直接走真 JSON，确认序列化不丢字段，
并覆盖"节点重启后继续写"。

## 三、业务流与故障演练

### 3.1 `verify_store_identity.py`

覆盖：上传 / 改块 / 置零 / 追加 / 截断 / 聚合 / 分解 / 删除，每一步都断言
"该变的变了、不该变的没变"（尤其不得触碰其他文件的 $\delta$）。

### 3.2 `verify_fault_drill.py`

三档递进，每档断言两件事：**该坏的坏了、不该坏的没坏**。

| 档位 | 故障 | 期望 |
|---|---|---|
| 一 | 一台节点掉线 | 读仍成功（其余副本），写按策略失败并说明原因 |
| 二 | 副本数不足 | 界面与接口给出"副本不足、存在不可逆风险"的明确结论 |
| 三 | 永久损毁 | 结论不可逆，且**不隐瞒**已经丢失的块 |

故障演练的立足点是"看到的失败是真代码的表现"，因此脚本断言的是**业务功能的真实反应**，
而不是"能不能模拟出来"。

## 四、跨文件合并的代价：实测与曲线

单文件路径下，证据合成只在**该文件自己的向量**上进行，代价与请求的下标集合 $I$ 有关。

跨文件路径（`VectorStore._prove_merged`）则不同，原因有两条：

1. 把 $S$ 抬到共同宇宙是可行的：$(S_I)^{E/E_f}=g^{E/e_I}=U'^{1/e_I}$；
2. $\Lambda$ **抬不动**：$\Lambda_I$ 的支撑集是**本文件的补集**
   （$\Lambda_I=(\prod S_j^{v_j})^{1/e_I}$，连乘只过本文件那些位置），
   它不含另一份文件的任何块。于是 `Agg` 里"用 $\prod\varphi_j^{v_j}$ 抵消交叉项"
   那一步没有东西可抵消，差额恰是"对方文件那些块的 $1/e_j$ 次方"，
   在隐藏阶群里求不出来（`svc/groups.generate_primes` 明确丢弃 $\varphi(N)$）。

要补齐那一半，只能**知道合并集里所有块的值**、在合并向量上重开。
因此这条路的代价是 $O(\sum_f |f|)$ 次大指数模幂，**与本次要验几块无关**，
只与涉及文件的总位置数有关。

复现方法：

```powershell
python -X utf8 scripts/bench_batch.py
```

该脚本测量同一批文件在"逐份验证"与"合并后一次验证"两种方式下的耗时，
用来判断批量验证在什么规模下划算。结论随机器与文件规模变化，以脚本当场输出为准，
不在文档里抄写固定数字。

## 五、增量聚合与一步分解（`verify_incremental_agg.py`）

回答两个代数问题：

1. 两段分别聚合再合并，是否与"一次性取全"**逐位相同**？
   即 $\mathrm{Agg}(\pi_I,\pi_J)\stackrel{?}{=}\pi_{I\cup J}$；
2. 从 $\pi_I$ 一步拆出 $\pi_K$（$K\subseteq I$），是否与当初直接聚出来的那一份逐位相同？

同时确认合并步骤**不向节点取任何数据**（响应中 `cert_count = 0`、`nodes_used = []`）。

失败含义：界面上"增量"二字的全部说法都不成立。

## 六、自动切块阶梯（`verify_segment_ladder.py`）

该函数决定每份新文件切多少块，而块数同时决定：

- 上传与验证的代价；
- "改一块"到底动了多少数据（块越大，改一块越像重传整份文件）。

判据：

1. 小文件 1 KB 起，大文件逐档上升；
2. 块数被压在目标值以内；
3. 档位表与前端 `src/utils/split.js` **同表**（两处任一改动，前端 `split.test.js` 会变红）。

## 七、接口层端到端（`_e2e_api.py`）

前提：`python -X utf8 scripts/start_all.py` 已把服务与节点拉起来。

流程：登录 → 上传 → 改块 → 追加 → 截断 → 检索 → 批量验证 → 增量聚合与分解 →
存储证明 → 故障演练（掉线 → 写失败（本次作废）→ 恢复 → 重做一次成功）。

它与 `verify_*` 的分工：后者多在进程内跑，前者打真实端口、真实节点进程、真实 SQLite。
"进程内全绿、跨进程全挂"这类问题只有它能抓到。

## 八、静态自检（四项）

| 脚本 | 钉住什么 | 失败后果 |
|---|---|---|
| `check_stage_names.py` | 前端步骤 `key` ↔ 后端 `with stage("…")` 埋点名逐字相等 | 静默丢耗时：那一步看着"不花时间" |
| `check_error_codes.py` | 后端 `ApiError` 码表 ↔ 前端 `data/errors.js` | 界面只显示原始码，用户读不懂 |
| `check_node_report_cache.py` | 节点现状的短 TTL 缓存与写操作后的失效时机 | 块分布图显示旧数据，像"上传变慢" |
| `check_js_wrap.py` | 「浏览器封 → Python 解」的跨实现互通 | 改口令后**双向锁死**：新口令过不了、旧口令解不开 |

`check_js_wrap.py` 需要先跑一次前端测试以产出落盘文件：

```powershell
npm --prefix frontend test
python -X utf8 scripts/check_js_wrap.py
```

## 十、判定标准与失败处理

1. **任何一项失败都不视为"环境问题"**：先看失败断言指向哪条不变式（见 [架构说明](架构说明.md) 第七节）。
2. **先跑静态自检，再跑行为验收**：步骤名与错误码对不上时，行为测试的失败信息会失真。
3. **跨进程问题优先用 `_e2e_api.py` 复现**：`verify_*` 全绿不能替代它。
4. **改了前端步骤或后端埋点，必须重跑 `check_stage_names.py`**。
5. **改了错误码，必须重跑 `check_error_codes.py`**。
6. **改了切块档位，必须同时更新 `src/utils/split.js` 与 `verify_segment_ladder.py` 的同表断言**。
