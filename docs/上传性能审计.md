# 上传为什么慢 —— 审计与提速方案（2026-09-30 实测）

> 本文件是**一次性能审计的记录**，所有数字都在本机（i7-14650HX / CPython 3.12 /
> Windows）实测得到，测量手段是项目自带的阶段秒表（`core/timing.py`）+ 微基准 +
> 隔离临时库，**没有猜**。
>
> 结论一句话：**慢的不是"文件大"，而是"块数多"，而且库里已有的块越多、每块越慢。**
> 将近 90%~97% 的时间花在"分发到节点"这一格，根因是一个
> **指数长度 ∝ 该节点已持有块数** 的模幂。

---

## 1. 实测：一次上传的时间都去哪了

### 1.1 真实部署（跨进程 4 台节点 + HTTP + 副本 2 + 1 KB/块）

`POST /api/files` 响应里的 `timings`（后端自报）：

| 阶段 | 20 块 × 1 KB | 占比 | 5 块 × 4 KB（同样 20 KB） | 占比 |
|---|---:|---:|---:|---:|
| 切块 / 生成密钥 IV | ~0 ms | 0% | ~0 ms | 0% |
| 逐块加密（SM4） | 0.8 ms | 0.0% | 0.5 ms | 0.0% |
| 算向量分量（SM3） | 0.3 ms | 0.0% | 0.2 ms | 0.0% |
| 封装块密钥（ECIES） | 118 ms | 1.6% | 29 ms | 0.8% |
| 承诺（push_update） | 417 ms | 5.8% | 64 ms | 1.7% |
| **分发到节点** | **6696 ms** | **92.5%** | **3606 ms** | **97.3%** |
| 落库（文件与块登记） | 7 ms | 0.1% | 6 ms | 0.2% |
| **合计** | **7247 ms** | | **3713 ms** | |

> 两行是**同一个 20 KB 文件**：1 KB 块切成 20 块、4 KB 块切成 5 块。
> 后者还在**更大**的库上跑（n 从 25 涨到 45），仍然快了近 2×。

### 1.2 隔离环境（同进程节点 + 临时库），看算法本身

32 块 × 1 KB：总 2372 ms（74 ms/块）

| 阶段 | ms | 占比 |
|---|---:|---:|
| 封装块密钥（ECIES） | 240 | 10.1% |
| 承诺（push_update） | 649 | 27.4% |
| **分发到节点** | **1422** | **59.9%** |
| 其余（切块/SM4/SM3/规划/落库） | ~60 | ~2.5% |

### 1.3 关键趋势：**同样的 16 块，库越大越慢**

同一个隔离库上连做三次 16 块上传：

| 上传前的全局块数 n | 挂钟 | ms/块 | 其中"分发到节点" |
|---:|---:|---:|---:|
| 32 | 7004 ms | 438 | 6304 ms |
| 48 | 9492 ms | 593 | 8615 ms |
| 64 | 12014 ms | 751 | 10957 ms |

⇒ 耗时长这样：**上传耗时 ≈ 常数 × 新增块数 k × 库里已有块数 n**。
这就是"我每次上传都很慢，而且越用越慢"的来源。

## 2. 根因（逐层追到那一行）

### 2.1 每块要做的三件密码学工作

1. **协调者承诺**：`svc/scheme.py::add_back`，每块 3 次模幂（两个 257 位指数 + 一个 256 位）；
2. **每个节点的状态吸收**：`vds/updates.py::_add_node_state`；
3. **ECIES 封装块密钥**：`core/keywrap.py::wrap_key`，微基准 **6.4 ms/块**。

### 2.2 模幂的耗时**只由指数位数决定**（实测）

| 指数 | 位数 | 一次 `pow(g, e, N)` |
|---|---:|---:|
| 单个素数 `e_j` | 257 | **1.18 ms** |
| `e_I`（4 个素数之积） | 1025 | 4.75 ms |
| `e_I`（16 个） | 4097 | 19.1 ms |
| `e_I`（64 个） | 16385 | 77.3 ms |
| `e_I`（256 个） | 65537 | 310.6 ms |

≈ **0.0047 ms/位**，严格线性。

### 2.3 那一行

`vds/updates.py::_add_node_state`（`add` 更新的公共实现，协调者与节点都调它）：

```python
e_I = e_of(primegen, node.I)              # ← 该节点**持有的全部下标**的素数之积
for j, v in zip(K, F_new):                # ← 对着**每个新位置**来一次
    t = shamir_trick(S2, S_j[j], e_I, primegen.get(j), N)
    Lam2 = Lam2 * pow(t, v, N) % N
```

`shamir_trick` 内部要先做同源自检 `pow(root_x, e_I, n)`，再用 Bézout 系数
`b`（|b| ≤ e_I/2）做 `root_x^b` —— **两次指数规模都是 `|I|` 个素数**。
于是：

* **每个新位置**的代价 ∝ **该节点已持有的块数** |I|；
* 4 台节点的 |I| 之和 = 副本数 × n = **2n**；
* 协调者又是**逐台串行** HTTP 推送（`core/transport.py::apply_append` 里一个 for 循环），
  每台各算一遍 ⇒ 总代价 ≈ **k × 2n**。

⇒ 一句总结：**上传的密码学代价是"新增块数 × 已有块数"量级（近似二次），与文件字节数几乎无关。**

### 2.4 顺便排除掉的"嫌疑人"

* **文件大小**：SM4 加密 1 KB = **0.033 ms**、SM3 = 0.011 ms ⇒ 1 MB 的加解密只要 ~33 ms。
  慢跟字节数没关系，只跟**块数**有关。
* **数据库**：落库 7 ms、分片规划 0.04 ms。
* **磁盘/网络**：本机回环，且 20 KB 只传一次。

## 3. 提速方案（按"性价比 / 风险"排序）

### A. 把块调大 —— 零代码风险，立刻可用

* 实测：同一个 20 KB 文件，**1 KB 块 7247 ms → 4 KB 块 3713 ms**（后者还在更大的 n 上跑）。
* 建议：把部署默认 `Settings.segment_bytes` 从 1024 调到 **4096**（或 8192）；界面上
  也可以用「按块大小」自己选。
* 代价：改块的粒度变粗（改一块 = 重写整个块）、每块的传输/内存变大（几 KB 无所谓）。
* **这条只是把常数改小，不改变"越传越慢"的趋势。**

### B. 批量 ShamirTrick —— 治本（把 O(k·n) 压成 O(n + k²)）

对同一批新位置，`t_j = S2^{1/e_j}` 可以这样一次算完：

```
1) 先把 k 个根 S_j 两两合并 ⇒ r_K = g^{E/e_K}       （指数只有 k 个素数 ⇒ 很便宜）
2) 再一次 shamir_trick(S2, r_K, e_I, e_K)          ← 只有这一次是 O(n)
3) 最后 t_j = r^{e_K/e_j}                          （小指数模幂 ⇒ O(k) 每次都便宜）
```

**实测（合成输入、真实素数规模、与旧实现对拍）**：

| 该节点已持有 | 本次新增 k | 逐个 | 批量 | 加速 | 值是否逐个相同 |
|---:|---:|---:|---:|---:|:--:|
| 16 | 16 | 725 ms | 568 ms | 1.28× | ✅ |
| 16 | 32 | 1471 ms | 1912 ms | 0.77× | ✅ |
| 64 | 16 | 2965 ms | 730 ms | **4.06×** | ✅ |
| 64 | 32 | 6454 ms | 2207 ms | 2.92× | ✅ |
| 256 | 16 | 12188 ms | 1289 ms | **9.46×** | ✅ |
| 256 | 32 | 23204 ms | 2654 ms | 8.74× | ✅ |
| 1024 | 16 | 46724 ms | 3533 ms | **13.22×** | ✅ |

* 交叉点大约在 **|I| ≈ k**：库里块少时批量反而略慢（自身开销），块一多就大幅领先。
* **数学完全没变**（只是换一种算法算同一组 `t_j`），产出的 `(S_I, Λ_I)` 逐位相同 ——
  这一点已用真实上传输入对拍验证过；落地时再用"新旧实现对拍 + 全链路验收"兜住。
* 改动面很小：只动 `vds/updates.py::_add_node_state` 一个函数（协调者与节点共用它）。

### C. 并行推送各节点 —— 与 B 正交，可叠加

* 现在 `apply_append` 是**逐台串行**（sync HTTP，一台算完再下一台）。
* 4 台节点各自独立计算 ⇒ 改成线程池并发，这一格最多 ÷4（本机 16 核足够）。
* 注意：**只有跨进程部署有效**；单进程模式（LocalTransport）受 GIL 限制，没有收益。
* 风险中等：要照顾"部分成功"的补推语义（现有 `_pending` / `retry_pending` 已处理）。

### D. ECIES 每次上传只封一把"文件级主密钥"

* 现在每块都做一次 ECIES（6.4 ms/块）：小库时占 ~10%，大库时可忽略（<1%）。
* 做法：每次上传封一把 32 字节主密钥，逐块密钥由 KDF(主密钥, 块序号) 派生；
  列存字段可以照旧放同一份封装（不必改库表）。
* **会改变密钥语义**（论文写的是"每段密钥用所有者公钥逐块封装"）⇒ 优先级最低，先不动。

### 建议顺序

**A（今天就能做）→ B（治本，收益最大）→ C（搭着 B 一起）→ D（可选，先放着）**
若只做一件：做 **B**。若能改配置：先做 **A** 再谈 B。
